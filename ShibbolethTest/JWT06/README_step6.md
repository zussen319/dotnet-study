# JWT 認証デモ ― ステップ6：SSO から JWT への橋渡し（統合の要）

ここまでのデモでは、SmartClient が**自分でユーザー名とパスワードを送って**トークンを得ていました。しかし本番の利用者は、メイン画面(.aspx)を開いた時点で**すでに SSO 認証済み**です。そこで SmartClient を起動するたびにパスワードを聞くのでは、SSO を導入した意味がありません。

ステップ6では、この2経路を合流させます。**SSO 認証済みのメイン画面が JWT の入手を仲介し、SmartClient には再入力させない**という仕組みです。

これが、これまでのステップが向かってきた到達点です。

```
  ブラウザ                    IIS + Shibboleth SP              トークンサービス      LDAP
     │                              │                                │              │
     │  ① メイン画面を開く          │                                │              │
     ├─────────────────────────────>│ REMOTE_USER 確定（SSO 済み）    │              │
     │                              │  ② 引換券をください            │              │
     │                              ├───────────────────────────────>│ 実在確認     │
     │                              │<───────────────────────────────┤<────────────>│
     │  ③ 起動リンク（引換券入り）   │        引換券                   │              │
     │<─────────────────────────────┤                                │              │
     │                                                               │              │
  SmartClient  ④ 引換券を JWT に交換（パスワード不要）                 │              │
     ├─────────────────────────────────────────────────────────────>│ 属性・ロール │
     │<─────────────────────────────────────────────────────────────┤<────────────>│
     │  ⑤ 以降は JWT で API を呼ぶ／切れたらリフレッシュで更新         │              │
```

> ## 実機での確認結果（重要・このステップで判明した点）
>
> **本ステップは実機で全項目の動作を確認済み。** 判明した点は以下の4件。
>
> **1. PowerShell の実行ポリシーでスクリプトがブロックされる**
> `.\Invoke-SsoLaunch.ps1` を実行すると `running scripts is disabled on this system`（`UnauthorizedAccess`）で拒否される。未署名スクリプトを実行させない Windows の既定の保護であり、スクリプトの内容とは無関係。**対処：その場限りで迂回する**のが学習用途では最も安全。
> ```powershell
> powershell -ExecutionPolicy Bypass -File .\Invoke-SsoLaunch.ps1
> ```
> 恒久的に許可する場合は `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`（管理者権限不要）。ただし `RemoteSigned` はダウンロード印（Mark of the Web）が付いたファイルを拒むため、必要に応じて `Unblock-File` を併用する。
>
> **2. スクリプトは ASCII のみで書くこと（文字コードの事故）**
> 日本語メッセージを含む版を Shift-JIS で保存して実行したところ、構文エラー（`The string is missing the terminator`／`Missing closing '}'`）で起動しなかった。**ファイル自体のバイト列は正常**（引用符の数は各行とも偶数）で、原因は**読み取り時の文字コードの誤解釈**。
> - **Windows PowerShell 5.1 は BOM の無い `.ps1` をシステムの ANSI コードページとして読む。** 日本語ロケールでない Windows では Shift-JIS が別の文字として解釈され、引用符の対応が崩れてパーサーが誤動作する。
> - 日本語を含めたいなら **UTF-8（BOM 付き）**で保存する（PowerShell 5.1 は BOM を見て判定する）。「UTF-8 BOM なし」が最も事故りやすい組み合わせ。PowerShell 7 なら BOM なしでも UTF-8 として読む。
> - **対処：スクリプトのメッセージを ASCII に統一した**（同梱の `Invoke-SsoLaunch.ps1` は純 ASCII）。実行環境のロケールや PowerShell のバージョンに左右されなくなる。日本語の説明は README（Markdown・UTF-8）側に置く。
> - **ステップ5の LDIF と同じ教訓**：環境をまたぐファイルは ASCII で書く。
>
> **3. スクリプトの `$ClientDir` 既定値を修正**
> 初版は `..\JwtDemoClient` だったが、スクリプトは `JWT06\` に置くため正しくは **`.\JwtDemoClient`**。同梱版では修正済みで、フォルダが見つからない場合のエラーメッセージも追加した。
>
> **4. 初回実行時に .NET の初回起動バナーが出る**
> 新しい環境で最初に `dotnet run` すると、Welcome メッセージ・テレメトリの案内・HTTPS 開発証明書のインストール通知が表示される。**異常ではない**。2回目以降は出ない。

## 中心となる考え方：なぜ「引換券」を挟むのか

一番素朴な発想は「メイン画面が JWT を取得して、SmartClient の起動パラメータに直接埋める」ですが、これは避けます。

**起動パラメータや URL は残りやすい**からです。ブラウザの履歴、Web サーバのアクセスログ、プロキシのログ、Windows のプロセス一覧（コマンドライン引数は他プロセスから見えます）、ショートカットファイル。JWT はそれ自体が「通行証」なので、有効期限が切れるまでの間、拾った人が本人になりすませてしまいます。

そこで、**一度使ったら無効になる短命の引換券**を渡します。

| | 引換券（ticket） | JWT（access token） |
|---|---|---|
| 有効期限 | 60秒 | 5分 |
| 再利用 | **できない**（一度きり） | 期限内は何度でも |
| 通り道 | 起動パラメータ（残りうる） | POST の応答ボディ（残らない） |
| 漏れたとき | ほぼ無害（既に使用済み/失効） | 期限まで悪用されうる |

この「短命・一回限りの引換券を、本命のトークンに交換する」形は、OAuth 2.0 の認可コードフローと同じ発想です。**特別な工夫ではなく、標準的な作法**だと理解しておくと、本番で Entra ID 側の仕組みと突き合わせるときに見通しが良くなります。

## もう一つの要点：リフレッシュトークン

JWT の有効期限は5分です。しかし SmartClient は何時間も起動しっぱなしになります。5分ごとに再起動させるわけにはいきません。

引換券は一度きりなので、2回目の交換には使えません。そこで、交換時に **リフレッシュトークン**（有効期限8時間）も一緒に渡し、JWT が切れたらこれで更新します。

- **アクセストークン（JWT）**：短命。毎回のリクエストに添える。漏れても被害が短時間。
- **リフレッシュトークン**：長命。更新のときだけ使う。普段は外に出ない。

本デモでは**使うたびに新しいものへ差し替える**（ローテーション）方式にしています。古いものは即座に無効になるため、盗まれた券が後から使われるリスクを下げられます。

## ★セキュリティ上の最重要ポイント（必ず読んでください）

このデモでは、SP が確定した利用者を **`X-Remote-User` という HTTP ヘッダー**で受け取っています。これは Shibboleth SP を立てずに動かすための**簡易な代替**です。

**ヘッダーは誰でも詐称できます。** この設定のまま外部から到達できる場所に置けば、誰でも任意の利用者になりすまして引換券を取得できてしまいます。認証が完全に無意味になります。

デモでは安全策として **ループバック（localhost）からの接続のみ許可**しています（`LoopbackOnlyForSso = true`）。それでも学習環境限定の措置です。

**本番では、次のどちらかで「SP が確定した値であること」を担保してください。**

- **(a) 引換券の発行エンドポイント自体を IIS 上に置き、Shibboleth SP で保護する。**
  SP がセットする `REMOTE_USER` はクライアントから詐称できません。ステップ17（複数 PLM 環境）で扱ったポート単位の `<Site>` 保護と同じ考え方で、このパスを SP 配下に置きます。**最も確実な方法です。**
- **(b) 発行エンドポイントを外部公開せず、メイン画面(.aspx)からのサーバ間通信のみに限定する。**
  加えて、共有シークレットや相互 TLS で「呼び出し元がその Web サーバであること」を検証します。

`LaunchSmartClient.aspx.sample` に、本番で .aspx がどう書かれるかの参考を置いてあります（`Request.ServerVariables["REMOTE_USER"]` を起点にする形）。

## 実行方法

### 準備

ApacheDS を起動し、サーバを起動します。

```powershell
cd JwtDemoServer
dotnet run
```

起動ログに次の2行が出ます。

```
[LDAP] ldap://localhost:10389  user=ou=people,...  group=ou=groups,...
[SSO ] 引換券発行: ヘッダー X-Remote-User / ループバック限定=True
```

### 実行（メイン画面の役をスクリプトが務める）

別のターミナルで、`JWT06` フォルダから実行します。**実行ポリシーのため `-ExecutionPolicy Bypass` を付けます**（上記「実機での確認結果 1」参照）。

```powershell
powershell -ExecutionPolicy Bypass -File .\Invoke-SsoLaunch.ps1
```

これが「SSO 認証済みのメイン画面が引換券を取得し、SmartClient を起動する」までを一気に再現します。一般利用者で試す場合は `-User 01PLM02@plm-lab.local` を付けます。

### スクリプトを使わない手動実行

実行ポリシーの変更を避けたい場合は、これで同じことができます（`JWT06` フォルダで実行）。

```powershell
# (1) メイン画面(.aspx)の役：引換券を取得する
$resp = Invoke-RestMethod http://localhost:5000/sso/ticket -Headers @{ "X-Remote-User" = "01PLM01@plm-lab.local" }
$ticket = $resp.ticket

# (2) SmartClient を起動する（引換券を渡す。パスワード入力なし）
cd .\JwtDemoClient
dotnet run -- $ticket
```

引換券は **60秒で失効**するので、(1) と (2) は続けて実行します。`dotnet run` に引数を渡す `--` は必須です（無いと `dotnet` 自身のオプションと解釈される）。

**注目していただきたいのは、SmartClient がパスワードを一切扱っていない点です。**

### 追加の確認（実機で確認済み・いずれも期待どおり 401）

下記3件は実機で実行し、**すべて `Unauthorized` が返ることを確認済み**。引換券の発行条件と失効が正しく効いていることの裏付けになります。

**SSO 未認証の場合** ― ヘッダーなしで引換券を要求すると 401 になります。

```powershell
try { Invoke-RestMethod http://localhost:5000/sso/ticket }
catch { "拒否された（期待どおり）: $($_.Exception.Response.StatusCode)" }
```

**存在しない利用者** ― ディレクトリにいない利用者には引換券を出しません。

```powershell
try { Invoke-RestMethod http://localhost:5000/sso/ticket -Headers @{ "X-Remote-User" = "nobody@plm-lab.local" } }
catch { "拒否された（期待どおり）: $($_.Exception.Response.StatusCode)" }
```

**期限切れの引換券** ― 引換券を取得して60秒以上待ってから交換すると 401 になります。

```powershell
$t = (Invoke-RestMethod http://localhost:5000/sso/ticket -Headers @{ "X-Remote-User" = "01PLM01@plm-lab.local" }).ticket
Start-Sleep -Seconds 65
try { Invoke-RestMethod -Uri http://localhost:5000/token/exchange -Method Post -Body (@{ ticket = $t } | ConvertTo-Json) -ContentType "application/json" }
catch { "拒否された（期待どおり）: $($_.Exception.Response.StatusCode)" }
```

**従来のパスワード方式との比較** ― 引数なしで起動すると、ステップ5までと同じ動きになります。

```powershell
cd JwtDemoClient
dotnet run
```

## HS256 と RS256（設計の整理）

持ち越してきた論点です。ここまでのデモはすべて **HS256（共通鍵）** で、1つの秘密鍵で署名も検証も行っています。

**判断の基準は「署名する人と検証する人が同じかどうか」です。**

- **HS256（共通鍵）が適する**：発行も検証も同じサービスが行う場合。鍵は1つだけで済み、構成が単純。**今回のデモや、トークンサービスと API が同一アプリなら、これで十分です。**
- **RS256（公開鍵）が必要になる**：**検証する側が複数に分かれる場合**。秘密鍵は発行者だけが持ち、検証側は公開鍵だけを持ちます。検証側が増えても秘密鍵を配る必要がなく、検証側が漏洩しても偽造トークンは作れません。

PLM 本番で RS256 を検討すべきなのは、次のような場合です。

- SmartClient 向けの Web サービスが**複数のサーバやサービスに分かれている**（それぞれが JWT を検証する）。
- **顧客ごとに環境が分かれ**、検証側が増えていく。
- **Entra ID が発行した JWT を直接検証する**構成に将来寄せる。Entra ID は RS256 で署名し、公開鍵を JWKS エンドポイントで公開します。この形に慣れておく意味は大きいです。

なお、SSO 側（SAML）では既に非対称鍵を使っています。IdP が秘密鍵でアサーションに署名し、SP がメタデータ経由で得た公開鍵（証明書）で検証する。**RS256 はこれと全く同じ構図**です。Windows 版手順書のメタデータ交換で行ったことが、そのまま JWT 側にも当てはまります。

実装上は `SymmetricSecurityKey` を `RsaSecurityKey`（または `X509SecurityKey`）に、`HmacSha256` を `RsaSha256` に差し替え、検証側には公開鍵だけを配る形になります。**本デモでは範囲を絞るため HS256 のままにしています**が、必要になった段階で差し替えは局所的です。

## 本番適用への対応表

| デモ | 本番（PLM） |
|---|---|
| `Invoke-SsoLaunch.ps1` | Shibboleth SP で保護された メイン画面 .aspx |
| `X-Remote-User` ヘッダー | SP がセットする `REMOTE_USER`（詐称不可） |
| `dotnet run -- <ticket>` | ClickOnce の起動 URL や配布設定に埋めた引換券 |
| メモリ上の引換券保管 | 複数台構成なら共有ストア（DB / Redis 等） |
| HTTP (localhost:5000) | HTTPS（SP と同じ TLS 方針） |
| HS256 | 検証側が分かれるなら RS256 |

**識別子については、ここまでの積み上げがそのまま効いています。** `REMOTE_USER` は `01PLM01@plm-lab.local`（メール形式）で来ますが、サーバの `LdapLookup` は `uid` と `mail` の両方で検索するため、どちらの形でも受けられます。ステップ4で「メール形式を `sub` に統一する」と決めたことで、SSO 経路と JWT 経路が**同じ識別子で合流**しています。

## トラブルシューティング

| 症状 | 原因の候補 | 対処 |
|---|---|---|
| 引換券の取得で 401 | ヘッダー名の誤り、または利用者がディレクトリに存在しない | `X-Remote-User` の綴りと、値が LDAP の uid か mail に一致するか確認 |
| 引換券の取得で 403 | ループバック以外からの接続 | 同じマシンから実行する（別マシンから試すなら `LoopbackOnlyForSso` を理解の上で調整） |
| 交換で 401 | 引換券が使用済み・期限切れ（60秒） | 取得から交換までを続けて実行する |
| `dotnet run` に引数が渡らない | `--` の付け忘れ | `dotnet run -- <ticket>` のように `--` が必要 |
| リフレッシュで 401 | 8時間経過、または既に使用済み（ローテーション） | 再度 SSO 経路から起動し直す |
| 503 が返る | ApacheDS 停止、または検索用アカウントの設定ミス | サービス稼働と `idp-reader` のバインドを確認 |

## 本番化に向けたメモ（随時追記）

- ✅ **識別子の統一**（ステップ4）／✅ **検索用アカウントの最小権限**（ステップ4）／✅ **クレーム名の変換対策**（ステップ5）
- ✅ **トークンの入手経路（本ステップで対応）**：引換券方式で、SSO 済み利用者に再入力させない。
- 🔺 **【本番で必須】引換券発行の保護**：ヘッダー信用をやめ、**SP 保護またはサーバ間通信限定**にする。デモのままでは絶対に公開しないこと。
- 🔺 **【本番で判断】HS256 → RS256**：検証側が複数に分かれるなら非対称鍵へ。Entra ID 直結を見据えるなら早めに慣れておく価値あり。
- **トークン保管の共有化**：Web サーバ複数台なら、引換券・リフレッシュトークンをメモリではなく共有ストアへ。
- **有効期限の設計**：引換券60秒／JWT 5分／リフレッシュ8時間はデモ値。業務の実態（作業時間、権限剥奪の反映速度）に合わせて決める。
- **ログアウトの扱い**：SSO のログアウト時に、発行済みのリフレッシュトークンをどう無効化するか。JWT は取り消せないので、リフレッシュ側で断つ設計になる。
- **ロールの鮮度**（ステップ5から継続）：権限変更はトークン更新時に反映される。有効期限の設計と一体で考える。
- **LDAP の暗号化**（据え置き）／**HTTPS 必須**（据え置き）／**鍵・シークレット管理**（据え置き）
- **環境をまたぐファイルは ASCII で**：LDIF（ステップ5）・PowerShell（本ステップ）の両方で、非 ASCII 文字による解釈失敗が発生した。配布・実行環境のロケールに依存しない書き方を既定にする。
