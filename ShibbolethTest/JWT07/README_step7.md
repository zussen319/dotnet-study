# JWT 認証デモ ― ステップ7：業務データとの連携（仕上げ）

最後のステップです。ここまでで確定した「**誰なのか**（識別子）」と「**何をしてよいのか**（ロール）」を使って、実際の業務データを取得します。検証環境の Oracle 19c（`scott/tiger`・EMP テーブル）に接続し、**ロールに応じて見えるデータを変えます**。

これにより、一連の流れが最初から最後までつながります。

```
  SSO で認証        引換券        JWT              権限判定         業務データ
  （Shibboleth）  →（一度きり）→（識別子＋ロール）→（403/絞り込み）→（Oracle EMP）
   ステップ6        ステップ6      ステップ4・5       ステップ5        ステップ7
```

**ロールによる違い**

| | 管理者（plm-admins） | 一般利用者（plm-users） |
|---|---|---|
| 見える**行** | 全部門（14件） | **自部門のみ** |
| 見える**列** | 給与(SAL)・歩合(COMM) **あり** | 給与は**そもそも返さない** |
| 集計 API | 呼べる | **403** |

> ⚠️ **本ステップは提案版です。** 実行して判明した点は、これまで同様この冒頭に追記して確定版にしてください。

### 2. Oracle 接続パッケージの追加

`JwtDemoServer.csproj` に **`Oracle.ManagedDataAccess.Core`** を追加します（同梱の csproj に反映済み）。これは Oracle が提供する .NET 用の接続ライブラリで、**Oracle Client のインストールが不要**な「マネージド」版です（sqlplus とは独立して動きます）。


## 利用者と部門の対応づけ

JWT で分かるのは「`01PLM01` という利用者である」ことまでで、その人が **EMP のどの部門に属するか**は別途決める必要があります。本デモではサーバ内の対応表で割り当てます。

```csharp
var userDepartment = new Dictionary<string, int>
{
    ["01PLM01"] = 20,   // RESEARCH（SMITH, JONES, SCOTT, ADAMS, FORD の5名）
    ["01PLM02"] = 30,   // SALES（ALLEN, WARD, MARTIN, BLAKE, TURNER, JAMES の6名）
};
```

ただし `01PLM01` は **plm-admins ロールを持つため全部門が見えます**。したがって実際の違いは次のように現れます。

- **01PLM01**（管理者）… 14件すべて＋給与あり
- **01PLM02**（一般）… DEPTNO=30 の**6件のみ**・給与なし

> **本番ではどうするか**：この対応表はデモの割り切りです。本番では **PLM のマスタ（DB のユーザーテーブル）が持つべき情報**で、コードに埋め込むものではありません。あるいは、部門情報を LDAP／Entra ID の属性として持たせ、ステップ5のロールと同じ経路で JWT に載せる方法もあります。**どこを「権限情報の正」とするか**は、PLM の既存設計に合わせて決めてください。

## 変更点の要点（サーバ）

- **`GET /api/employees`**：JWT のロールを見て、管理者なら全件・給与込み、一般利用者なら自部門のみ・給与抜きで返します。
- **見せない列は、そもそも SELECT しない**：一般利用者向けの SQL には `SAL`・`COMM` を含めていません。取得してからクライアント側で隠すのではなく、**サーバが最初から取らない**のが安全です（表示を消しただけでは、通信内容を見れば分かってしまいます）。
- **バインド変数を使う**：部門の絞り込みは `WHERE DEPTNO = :deptno` とパラメータで渡し、文字列連結はしません。**SQL インジェクション対策**であり、ステップ4の LDAP フィルタのエスケープと**まったく同じ発想**です。
- **`GET /api/employees/summary`**：`AdminOnly` ポリシーで保護した集計 API。一般利用者は 403。
- **部門が未定義の利用者は 403**：対応表に無い一般利用者には、業務データを見せません（「分からないから全部見せる」は危険な設計です）。

## 実行方法

1. **ApacheDS と Oracle を起動**しておく。
2. サーバ起動：`cd JwtDemoServer` → `dotnet run`。起動ログに3行（LDAP／SSO／ORACLE）が出ます。
3. `JWT07` フォルダで、管理者・一般利用者の順に実行します。

```powershell
# 管理者（01PLM01）
powershell -ExecutionPolicy Bypass -File .\Invoke-SsoLaunch.ps1

# 一般利用者（01PLM02）
powershell -ExecutionPolicy Bypass -File .\Invoke-SsoLaunch.ps1 -User 01PLM02@plm-lab.local
```

**確認の勘所は3点です。**

1. **件数が違う**（14件 vs 6件）… 同じ API を呼んでいるのに、見える行が権限で変わる。
2. **列が違う**（給与欄の有無）… 一般利用者には、そもそもサーバが給与を返していない。
3. **[3] が 403**（一般利用者のみ）… ステップ5で学んだ認可が、業務データにも効いている。

サーバ側のコンソールにも `[ORACLE] 01PLM02 に 6 件を返却（DEPTNO=30・給与なし）` のようなログが出ます。

## トラブルシューティング

| 症状 | 原因の候補 | 対処 |
|---|---|---|
| `ORA-12541: TNS:no listener` | Oracle のリスナーが停止 | サービスを確認。`sqlplus` で接続できるか先に試す |
| `ORA-01017: invalid username/password` | 接続文字列の誤り | `User Id=scott;Password=tiger;Data Source=localhost:1521/xe` を確認 |
| `ORA-00942: table or view does not exist` | scott スキーマに EMP が無い | `sqlplus scott/tiger` で `select * from emp;` を確認 |
| 503 が返る | Oracle か LDAP に接続できない | サーバのコンソールログにエラー内容が出る |
| パッケージの復元に失敗 | バージョン指定が環境に合わない | NuGet で最新の 23.x 系を選び直す |
| 一般利用者が 403（employees） | 対応表に uid が無い | `userDepartment` に uid が登録されているか確認 |

## 全7ステップの振り返り

| ステップ | 学んだこと | PLM 本番での対応 |
|---|---|---|
| 1 | JWT の発行・検証（署名・期限・改ざん検知） | SmartClient 向け Web サービスの基礎 |
| 2 | クライアントからの往復 | SmartClient の通信部分 |
| 3 | トークン管理（使い回し・自動再取得） | 長時間動くクライアントの実装 |
| 4 | LDAP 認証と**識別子の統一** | SSO と同じユーザー源・同じ識別子 |
| 5 | ロールによる**認可**（401 と 403 の違い） | 権限制御の基礎 |
| 6 | **SSO → JWT の橋渡し**（引換券） | 2経路の統合（本番の要） |
| 7 | 権限に応じた**業務データ**取得 | PLM 本来の処理 |

**2つの経路は、次のように合流しています。**

| | ブラウザ画面（.aspx） | SmartClient |
|---|---|---|
| 認証 | Shibboleth SP | JWT（元は SSO） |
| 識別子 | `REMOTE_USER` | `sub` クレーム |
| **値** | **`01PLM01@plm-lab.local`** | **`01PLM01@plm-lab.local`**（同一） |
| 権限 | SP 経由の属性 | `role` クレーム |
| データ | 同じ PLM の DB | 同じ PLM の DB |

ステップ4で「メール形式を識別子の正とする」と決めたことで、**両経路が同じ値で合流**しています。本番では IdP が自前構築のものから顧客の Entra ID に変わりますが、**SP 側の考え方（`REMOTE_USER` を確定する）も、JWT 側の考え方（`sub` とロールを載せる）も変わりません**。

## 本番化に向けたメモ（最終版）

これまでの各ステップで積み上げてきた持ち越し課題の一覧です。**本番適用時のチェックリスト**として使えます。

### 対応済み（デモで実践）

- ✅ **識別子の統一**（ステップ4）：メール形式で SSO/JWT/Entra が一致
- ✅ **検索用アカウントの最小権限**（ステップ4）：管理者ではなく `idp-reader`
- ✅ **クレーム名の変換対策**（ステップ5）：取り出しは常に多候補で
- ✅ **トークンの入手経路**（ステップ6）：引換券方式で再入力なし
- ✅ **SQL インジェクション対策**（ステップ7）：バインド変数を使う
- ✅ **見せない列は取得しない**（ステップ7）：表示で隠すだけにしない

### 本番で必須の対応

- 🔺 **引換券発行の保護**：ヘッダー信用をやめ、**SP 保護またはサーバ間通信限定**に。デモのままでは絶対に公開しない（ステップ6）
- 🔺 **HTTPS 必須**：Bearer トークンは必ず HTTPS で運ぶ
- 🔺 **LDAP の暗号化**：LDAPS(636) か StartTLS へ
- 🔺 **鍵・シークレット管理**：署名鍵・LDAP バインド情報・**DB 接続文字列**を設定/シークレットストアへ
- 🔺 **DB アカウントの最小権限**：`scott` は学習用。本番は必要な表への必要な権限だけを持つ専用アカウントに

### 本番で判断が必要

- **HS256 → RS256**：検証側が複数に分かれる／Entra ID 直結を見据えるなら非対称鍵へ（ステップ6）
- **権限情報の「正」をどこに置くか**：部門・ロールを LDAP/Entra の属性で持つか、PLM のマスタで持つか（ステップ7）
- **有効期限の設計**：引換券60秒／JWT 5分／リフレッシュ8時間はデモ値。業務実態と権限剥奪の反映速度から決める
- **ログアウトの扱い**：SSO ログアウト時に、発行済みリフレッシュトークンをどう無効化するか
- **トークン保管の共有化**：Web サーバ複数台なら共有ストア（DB/Redis 等）へ
- **接続の堅牢化**：LDAP・Oracle ともタイムアウト、接続プール、リトライ方針
- **ロールの鮮度**：権限変更はトークン更新時に反映される（有効期限の設計と一体）

### 環境面の教訓

- **環境をまたぐファイルは ASCII で**：LDIF（ステップ5）・PowerShell（ステップ6）の両方で、非 ASCII による解釈失敗が発生した

## この先の展開（参考）

学習としての7ステップはここで完結です。組織の開発環境へ適用する段階で、次のような発展が考えられます。

- **実際の PLM 画面との結合**：`whoami.asp` 相当のメイン画面を SP 保護下に置き、`LaunchSmartClient.aspx.sample`（ステップ6）の考え方で実際の SmartClient を起動する。
- **Entra ID への切り替え**：自前 IdP を顧客の Entra ID メタデータに差し替える。SP 側の設定変更が中心で、**JWT 側はほぼ変更なし**のはず。ここまでの構成なら、その見通しが立てられます。
- **複数 PLM 環境の並行運用**：Windows 版手順書 §17 の構成（HTTP は従来認証・HTTPS を SSO 用に新設）と、本デモのトークンサービスをどう共存させるか。
- **移行期間の設計**：従来の「独自認証」と SSO/JWT を並行稼働させる期間の扱い（本デモで `/token` のパスワード方式を残してあるのは、この検討の材料になります）。
