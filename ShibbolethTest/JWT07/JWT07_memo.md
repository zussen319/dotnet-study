## このステップで確認できること

同じ `GET /api/employees` を呼んでも、**権限によって結果が変わります**。

- **01PLM01**（管理者）… 14件すべて、給与(SAL)・歩合(COMM)込み
- **01PLM02**（一般）… DEPTNO=30 の**6件のみ**、給与なし。集計 API は **403**

`01PLM01` は plm-admins を持つため全部門が見える点にご留意ください。部門の対応表が効いてくるのは 01PLM02 側です。

設計上、意識していただきたい点が2つあります。

**見せない列は、そもそも SELECT していません。** 一般利用者向けの SQL には `SAL`・`COMM` を含めていません。取得してから画面で隠すのでは、通信内容を見れば分かってしまいます。サーバが最初から取らないのが安全です。

**部門の絞り込みはバインド変数**（`WHERE DEPTNO = :deptno`）で渡し、文字列連結していません。SQL インジェクション対策で、ステップ4の LDAP フィルタのエスケープと同じ発想です。

## 準備で1点だけ

`Oracle.ManagedDataAccess.Core` を追加します（csproj に反映済み、`23.6.0` 指定）。Oracle Client のインストールが不要なマネージド版なので、sqlplus とは独立して動きます。復元に失敗する場合は、NuGet で提示される最新の 23.x 系を選び直してください。バージョン差はこのデモの動作に影響しません。

## 対応づけについての補足

`userDepartment` の対応表はコードに直書きしていますが、これはデモの割り切りです。**本番では PLM のマスタ（DB のユーザーテーブル）が持つべき情報**で、コードに埋め込むものではありません。あるいは部門を LDAP／Entra ID の属性として持たせ、ステップ5のロールと同じ経路で JWT に載せる方法もあります。「どこを権限情報の正とするか」は既存設計に合わせてご判断ください。README に選択肢として記載しています。
