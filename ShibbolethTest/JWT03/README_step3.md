# JWT 認証デモ ― ステップ3：クライアント側のトークン管理

ステップ2のクライアントは、操作のたびにトークンを取り直していました。ステップ3では、実際の SmartClient に近づけて **「1回取得 → 有効期限まで使い回す → 切れる/弾かれたら自動で取り直す」** というトークン管理を入れます。

- **変更するのはクライアントだけ**（`JwtDemoClient.cs`）。**サーバ（`JwtDemoServer.cs`）はステップ1から変更なし**。
- 学ぶのは2つの再取得のしかた：
  - **先回り（proactive）**：呼ぶ前に「期限が近い/切れている」なら取り直す。
  - **後追い（reactive）**：それでも `401` が返ったら取り直して1回だけ再試行する。

> ⚠️ **本ステップは提案版です。** ステップ1・2と同様、実機で動かして判明した点（ポート・挙動・.NET 版差など）はこの冒頭に追記して確定版にしてください。

## 実行すると何が起きるか

```
=== JWT 認証デモ クライアント（ステップ3：トークン管理）===
接続先: http://localhost:5000

[1] whoami を3回連続で呼びます（トークンは1回だけ取得されるはず）
        （/token でトークン取得。約300秒有効。取得回数=1）
    1回目: 成功 (200) username=01PLM01
    2回目: 成功 (200) username=01PLM01
    3回目: 成功 (200) username=01PLM01
    → /token を呼んだ回数: 1（1 が期待値＝使い回せている）

[2] トークンを強制的に期限切れにして呼びます（呼ぶ前に自動で取り直すはず）
        （/token でトークン取得。約300秒有効。取得回数=2）
    結果: 成功 (200) username=01PLM01
    → /token を呼んだ回数: 2（2 に増える＝期限前に取り直した）

[3] キャッシュを壊れたトークンに差し替えて呼びます（401 を受けたら取り直して再試行するはず）
        （401 を受信 → トークンを取り直して再試行します）
        （/token でトークン取得。約300秒有効。取得回数=3）
    結果: 成功 (200) username=01PLM01
    → /token を呼んだ回数: 3（3 に増える＝401 を受けて取り直した）

=== 完了 ===
```

ポイントは **「/token を呼んだ回数」** です。[1] で 3 回呼んでも取得は 1 回だけ（使い回せている）、[2] と [3] でそれぞれ 1 回ずつ増える（正しく取り直している）ことを、この数字で確認できます。

## コードの見どころ（JwtDemoClient.cs）

- **`TokenProvider` クラス**：トークンの取得・キャッシュ・失効判定を1か所に集約。実際の SmartClient が内部に持つ「トークン管理」に相当します。
- **`GetValidTokenAsync()`**：`_token` があり、かつ `now < 期限` なら**使い回す**（`/token` を呼ばない）。そうでなければ取得します。＝**先回り（proactive）**。
- **`expires_in` → 絶対期限 − 安全マージン**：サーバが返す `expires_in`（秒）から絶対期限を計算し、`SafetyMargin`（30秒）だけ手前で切れた扱いにします。**「送った瞬間に期限切れ」を避ける**ための実務的な工夫です（SSO 構築で扱った clock skew と同じ発想）。
- **`401` → `Invalidate()` → 再試行**：`CallWhoAmIAsync` は `401` を受けたら手元トークンを捨て、取り直して**1回だけ**再試行します。＝**後追い（reactive）**。先回り判定をすり抜けた失効（サーバ再起動・鍵変更・トークン失効など）に備える保険です。
- `ForceExpireForDemo()` / `InjectBrokenTokenForDemo()` は**デモ専用の小細工**（5分待たずに再取得を体験するため）。本物の SmartClient には不要です。

## 実際の SmartClient との対応

| デモ | 実際の SmartClient |
|---|---|
| `TokenProvider` にトークンを保持 | クライアントがトークンを保持（有効期限まで使い回す） |
| `GetValidTokenAsync` で期限を見て判断 | 毎回取り直さず、期限が近ければ取り直す |
| `401` で `Invalidate` → 再試行 | トークンが弾かれたら再取得（or 再ログイン） |
| 安全マージン 30 秒 | 時刻ズレ・遅延を見込んだ余裕 |

## 本番化に向けたメモ（随時追記）

このデモを実運用へ持っていく際の“持ち越し課題”を、ステップを追うごとにここへ足していきます（今は対応不要）。

- **HTTPS 必須**：Bearer トークンは Authorization ヘッダーで運ばれるため、**本番では必ず HTTPS**にします（デモの `http://localhost` は割り切り）。SSO 側で 443/8443 を TLS 化したのと同じ考え方。
- **鍵/シークレットの管理**：署名鍵はデモではコードに直書き。本番は設定/シークレットストアへ。HS256 の共通鍵は「発行者＝検証者」でのみ共有する。
- **時刻同期（clock skew）**：`exp`/`nbf` の判定は時刻に敏感。SSO 構築時と同じく、発行側・検証側の時計を揃える（安全マージンは補助であって代替ではない）。
- **【ステップ4で扱う】識別子の統一**：現在 `sub`/`username` は `01PLM01`。SSO(.aspx) 側の `REMOTE_USER` は `01PLM01@plm-lab.local`。両経路が同じ PLM の認可に入るので、どちらを正とするか（`@` の前で正規化する等）を LDAP 接続時に決める。
- **【ステップ6で扱う】トークンの入手経路**：本番の利用者はメイン画面(.aspx)で既に SSO 認証済み。SmartClient に**再ログインさせずに**トークンを渡す“橋渡し”をどう作るか。
- **【ステップ6で扱う】HS256 と RS256**：発行者＝検証者が同一の間は HS256 で十分。検証が別サービスに分かれる／Entra ID が発行する本番像に寄せる段階で、公開鍵で検証する RS256（非対称）が近い類推になる。

## 次のステップ（予定）

- **ステップ4**：サーバの `/token` の初回認証を、固定ユーザーから **ApacheDS(LDAP)** 接続へ差し替え（SSO と同じユーザー源に接続）。ここで「識別子の統一」を確定する。
- **ステップ5**：JWT に**ロール/属性**を載せ、それに応じて処理・アクセス制御を分岐（SSO 側の属性解放との対応を意識）。
- **ステップ6（統合の要）**：SSO 認証済みのメイン画面(.aspx)が JWT を発行/取得して SmartClient に引き渡す“橋渡し”。ここで HS256↔RS256・署名者・Entra ID の本番像を扱う。
- **ステップ7（発展）**：検証済み API が業務データ（Oracle 19c：`scott/tiger`・EMP 等）をユーザー権限で返す。
