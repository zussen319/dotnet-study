# PLM システム SSO/JWT 対応プロジェクト 全体サマリ

このドキュメントは、これまでの検討・実装の**全体像と要点**をまとめたものです。新しいチャットに経緯を引き継ぐ際や、全体を俯瞰したいときに参照します。

各段階の詳細な手順は個別の手順書・README にあるため、ここでは**概略と、後から思い出したい判断・知見**に絞っています。

---

## 0. 背景と目的

自組織で開発・提供している **PLM システム**の認証を、**独自認証から Microsoft Entra ID ＋ Shibboleth SSO へ移行**する。

PLM には2種類のクライアントがある。

| クライアント | 形態 | 認証方式 |
|---|---|---|
| ブラウザ画面 | `.aspx`（WebForms）のポップアップ画面 | **Shibboleth SSO** |
| SmartClient | ダウンロード型アプリ（ClickOnce）→ Web サービスと通信 | **JWT** |

**目標**：ブラウザで SSO 認証すれば、SmartClient は再ログインせず（パスワード入力なしで）業務 API を呼べる状態にする。

## 2. 学習段階：SSO 環境の構築

Shibboleth による SSO の仕組みを理解するため、検証環境を構築した。**2つの版**がある。

| 版 | 内容 |
|---|---|
| **WSL版** | WSL2 上に構築した最初の学習環境 |
| **Windows版** | Windows ネイティブに構築した版（本番に近い） |

### 確定した環境情報

| 項目 | 値 |
|---|---|
| ドメイン | `plm-lab.local` |
| SP（サービス提供側） | `sp.plm-lab.local`（IIS、HTTPS 443） |
| IdP（認証側） | `idp.plm-lab.local`（Tomcat、8443） |
| LDAP | ApacheDS、ポート 10389、ベース `dc=example,dc=com` |
| 利用者 | `01PLM01` / `01PLM02`（Joe アカウント：ユーザー名＝パスワード） |
| LDAP 検索用 | `uid=idp-reader,ou=people,dc=example,dc=com` |
| 内部 CA | `PLM-Lab Root CA` |
| メール属性 | `01PLM01@plm-lab.local` |

### 主な知見

- **SP が `REMOTE_USER` を確定する**のが認証の起点。この値はクライアントから詐称できない
- Windows版では `shibboleth2.xml` の `<ISAPI><Site id="1" name="sp.plm-lab.local" .../>` により、**IIS サイト ID への全リクエストが `sp.plm-lab.local` として扱われる**（`localhost` でアクセスしても SP 保護が掛かる）
- Windows Server 特有の注意点は Windows版手順書の §18 に集約（TLS 1.2、OpenSSL の `-legacy` 等）

## 3. 学習段階：JWT 実装案の検討（ステップ1〜7）

SmartClient を JWT で認証する仕組みを、段階的に検証した。**この段階は .NET 10 / C# / VS2026** で実施（学習目的）。

| ステップ | 内容 | 主な知見 |
|---|---|---|
| 1 | JWT サーバ（HS256、固定ユーザー） | **.NET 8+ は `JsonWebTokenHandler` を使う**。`DefaultInboundClaimTypeMap` をクリアしないとクレーム名が URI 化する。クレームは複数候補で取得（`sub` → `NameIdentifier` → `Identity.Name`） |
| 2 | コンソール版 SmartClient クライアント | |
| 3 | トークンの寿命管理（再利用・更新） | |
| 4 | `/token` を LDAP 連携（search-then-bind） | `sub` をメール形式にして `REMOTE_USER` と一致させる。`ClaimTypes.Email` もフォールバック候補に |
| 5 | LDAP グループ → ロール → 認可（401 vs 403） | `RoleClaimType="role"` が必要。LDIF は ASCII のみ（日本語で `ERR_13247`） |
| 6 | SSO → JWT の橋渡し（引換券方式） | **一度きり・短命の引換券**で JWT を受け渡す。HS256 と RS256 の違いを整理。PowerShell は ASCII のみ |
| 7 | Oracle 19c の業務データをロール別に取得 | バインド変数で SQL インジェクション対策。ロールで可視範囲を制御 |

### 繰り返し現れた教訓

**環境をまたぐファイル（LDIF、PowerShell、.aspx）は ASCII か、明示的に UTF-8（BOM付き）にする。** 日本語ロケールでない環境では、文字コードの取り違えで文字化けや解析エラーが起きる。

## 4. 実装段階：PLM への適用（フェーズ1〜7）

### ★最重要の方針転換：.NET Framework 4.8 / C# へ

学習段階は .NET 10 だったが、実装段階で **.NET Framework 4.8 / C#** に切り替えた。理由：

- **VS2019 は .NET 10 をビルドできない**（組織の開発環境は VS2019 + .NET Framework 4.8）
- **顧客サーバに新しいランタイム依存を持ち込まない**（4.8 は Windows 同梱）
- **`.aspx`（WebForms）は 4.8 でしか動かない**

開発言語は VB.NET ではなく **C#** を採用（学習・検証目的のため問題なし）。開発は **VS2026 で 4.8 をターゲット**にして進行（VS2026 でも 4.8 の開発は可能）。最終的には組織の VS2019 へ。

**副次的効果**：4.8 統一により、当初の「.aspx＋ASP.NET Core の2アプリ構成」が **WebForms と Web API 2 を同居させた1アプリ構成**に簡素化できた。これにより、ステップ6で懸念した「X-Remote-User ヘッダー詐称」のリスクが**原理的に消えた**（同一プロセス内で直接呼ぶため）。

### アーキテクチャ

```
https://sp.plm-lab.local/PLM/          単一の ASP.NET 4.8 アプリ
    ├─ Default.aspx        メイン画面        【SP 保護あり】
    ├─ /PLM/api/*          Web API 2         【SP 保護なし】
    └─ /PLM/smartclient/   ClickOnce 配布     【SP 保護なし】
```

**保護をパス単位で分ける**のが設計の核心。SmartClient は SSO Cookie を持たないため、`/api` と `/smartclient` は SP 保護から外し、`/` だけ保護する。`shibboleth2.xml` で入れ子の `<Path>` により実現。

### 各フェーズの概要

| フェーズ | 内容 | 状態 |
|---|---|---|
| **1** | ClickOnce の引数受け渡しスパイク | 完了。`ApplicationDeployment.ActivationUri` で引換券が届くことを確認。オンライン専用＋「URLパラメータ許可」が必須 |
| **2** | IIS のサイト構成と SP のパス単位保護 | 完了。`/PLM` 配下に配置。REMOTE_USER 取得を確認 |
| **3** | 引換券の発行と JWT の交換 | 完了。ブラウザ→引換券→SmartClient→JWT→API の往復が通る |
| **4** | 署名鍵を Windows 資格情報マネージャーへ | 完了。Web.config の平文から移行 |
| **5** | 組織環境での再現準備 | 手順作成済み。`.slnx`→`.sln` 変換、環境固有値の洗い出し |
| **6** | 本番想定の整備 | 手順作成済み。低権限アカウント、診断無効化、設定の本番化 |
| **7** | 顧客環境への適用（Entra ID） | 手順作成済み。IdP を Entra ID に差し替え |

### 一連の動作フロー（フェーズ3で確立）

```
ブラウザで SSO 認証
    ↓ REMOTE_USER 確定（SP がセット・詐称不可）
Default.aspx が引換券を発行（TicketStore.Issue を同一プロセス内で直接呼ぶ）
    ↓ 起動リンクに埋め込む（一度きり・60秒）
SmartClient 起動（ClickOnce）
    ↓ 引換券を JWT に交換（POST /PLM/api/token/exchange、パスワード不要）
保護 API を呼ぶ（GET /PLM/api/whoami、JWT 検証）
    ↓
利用者確定（= ブラウザ側の REMOTE_USER と同じ値）
```

## 5. 実装段階で確定した主な技術判断・知見

### 開発環境

- **言語バージョンは触らない**：.NET Framework プロジェクトは自動で C# 7.3（VS2019 互換）。「Automatically selected」のままが正解
- **VS の個別コンポーネント**：`.NET Framework project and item templates` が必要（ワークロードだけでは不足）。「Additional project templates (previous versions)」は VS2026 には存在しない
- **文字化け対策**：`.aspx` は UTF-8 BOM 付き＋ `Web.config` に `<globalization fileEncoding="utf-8" .../>`。日本語ロケールでない Windows で `.aspx` の日本語が化けるため

### IIS・デバッグ

- **デバッグは「w3wp.exe にアタッチ」方式に統一**。F5（ローカル IIS）は SSO 環境では成立しない（VS が `localhost` しか受け付けない、`localhost` も SP 保護下、`0x80004005` で失敗、Windows 認証を足しても解決せず）
- ソースフォルダを直接 IIS にマッピングするため、`IIS_IUSRS` に読み取り権限が必要
- `App_Data` には書き込み権限が必要（ログ出力用）

### WebForms 固有

- **`.aspx` を差し替えるときは `.designer.cs` も一緒に**（コントロール宣言があるため。忘れると `The name 'xxx' does not exist`）
- **コントローラーやファイルは「プロジェクトに含める」必須**（エクスプローラーでコピーしただけでは `No type was found` 等）

### ClickOnce

- **オンライン専用＋「URLパラメータを渡すことを許可」が必須**。インストール型だと2回目以降パラメータを受け取れない
- **起動ページ（launch）は Web アプリ側（`/PLM/`）に置く**。ClickOnce の発行先には配布されない。結果的に「起動ページは SP 保護下、本体は保護外」という本番構造になる
- 再発行時はバージョンが上がることを確認。古いまま同一バージョンだと再ダウンロードされない（`rundll32 dfshim CleanOnlineAppCache` でキャッシュクリア）

### JWT・引換券・署名鍵

- **引換券**：`TicketStore`（プロセス内・一度きり・短命）。`Issue`/`Consume`/`Count` の小さな窓口に閉じてあり、複数台構成では共有ストアに差し替えるだけでよい
- **署名鍵**：Windows 資格情報マネージャー（`PlmSsoDemo/JwtSigningKey`）。**資格情報は利用者ごと**なので、①アプリプールを専用アカウントで動かす②そのアカウントで登録③「ユーザープロファイルの読み込み」を True、の3点が揃わないと読めない
- 取得失敗時は Web.config に**戻さずエラーで停止**（平文の鍵で気づかず動き続けるのを防ぐ）

### デバッグ用の工夫（本番に影響しない）

- **`#if DEBUG` で本番の動作を変えずに開発を楽にする**手法を活用
  - 引換券の有効期限を DEBUG ビルドで延長（例：3600秒）。Release では設定値（60秒）
  - JWT の有効期限も同様に延長可能
  - DEBUG ビルド限定で「引換券入力ダイアログ」を表示（URL を貼ると `ticket=` 以降を自動抽出）

### フォルダ運用

- 各フェーズを別フォルダ（`SSO-Impl01`〜）にコピーして進行。動作する状態がフェーズごとに残る
- 移行時は：IIS の物理パス2箇所（`/PLM` と `/PLM/smartclient`）、フォルダ権限、ClickOnce のバージョンを確認

## 9. 一貫して効いている設計思想

このプロジェクト全体を貫く判断。顧客展開で活きる。

- **認証を SP に集約**：アプリは `REMOTE_USER` だけを見る。IdP を Entra ID に差し替えてもアプリは無変更
- **1アプリ構成**：ヘッダー詐称リスクが原理的に無い、構成がシンプル
- **引換券方式**：URL やログに JWT（通行証）が残らない（OAuth 認可コードと同じ発想）
- **秘密を設定ファイルに置かない**：署名鍵は資格情報マネージャー
- **識別子は対応表で解決（推奨）**：メール・ドメイン変更に強い
- **環境固有値は明示、外出しはしない**：再現目的では「どこを変えれば動くか」が明確な方がよい
- **`#if DEBUG` で本番を変えず開発を楽に**：デバッグ用の細工が本番に混入しない
