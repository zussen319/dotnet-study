# フェーズ7：顧客環境への適用（Entra ID 連携）

フェーズ6までで、本番相当の状態に整いました。フェーズ7は最終段階で、**自前の IdP（Shibboleth IdP）を顧客の Entra ID に差し替え、実際の顧客環境で動かす**ことが目標です。

これまでのフェーズが「自分の管理下で作る」ものだったのに対し、フェーズ7は**顧客の IT 部門との協働**が前提になります。技術作業そのものより、**事前の調整と確認**が成否を分けます。

> ⚠️ **本フェーズは提案版です。** 実際の顧客環境は個別性が高いため、本書は「考え方と進め方の枠組み」を示すものです。具体値は顧客ごとに確定させてください。

---

## 全体像：何が変わり、何が変わらないか

**この構成の最大の利点は、認証基盤を差し替えても大部分が変わらないことです。**

```
【学習・検証環境】                    【顧客環境】
Shibboleth IdP（自前）      →         Entra ID（顧客）
        ↓ SAML                                ↓ SAML
Shibboleth SP（IIS）        =         Shibboleth SP（IIS）★変わらない
        ↓ REMOTE_USER                         ↓ REMOTE_USER
PLM アプリ（/PLM）          =         PLM アプリ（/PLM）  ★変わらない
        ↓ 引換券 → JWT                        ↓ 引換券 → JWT
SmartClient                 =         SmartClient         ★変わらない
```

**SP が `REMOTE_USER` を確定する**という一点が同じである限り、その先（引換券・JWT・SmartClient）は一切変わりません。差し替わるのは **IdP と SP の間の信頼関係**だけです。

これは学習の初期から一貫して設計してきたことの成果です。「認証の入口は SP に集約し、アプリは REMOTE_USER だけを見る」という構造が、この差し替えを可能にしています。

## 手順

### 第1段階：サーバ環境の構築（Windows Server 2022）

学習環境は Windows 11 でしたが、顧客のサーバは Windows Server 2022 になる想定です。

**参照**：Windows 版 SSO 構築手順書、特に §18（Windows Server 2016 での実機知見）

Windows Server 特有の注意点は、Server 2016 で確認済みの内容が参考になります。

- **TLS 1.2 の明示的な有効化**（既定で無効な場合がある）
- **OpenSSL の `-legacy` オプション**（証明書変換時）
- **既存サイトによるサイト ID のずれ**（`shibboleth2.xml` の `<Site id="...">` の確認）
- ファイアウォールの規則（IdP との通信、クライアントからの HTTPS）

**✔ 確認**：IIS が動作し、HTTPS でアクセスできる

### 第2段階：Shibboleth SP の導入と Entra ID との連携

ここが学習環境と最も異なる部分です。

**(a) SP を導入する**（学習環境と同じ手順）

**(b) Entra ID にアプリケーションを登録する**（顧客の IT 部門が実施）

顧客側で、エンタープライズアプリケーション（SAML）として PLM を登録してもらいます。この際、次を伝えます。

- SP のエンティティ ID（メタデータに記載）
- アサーション コンシューマー サービス（ACS）URL
- 必要な属性（NameID、メールアドレス等）

**(c) メタデータを交換する**

- 顧客から：Entra ID のフェデレーション メタデータ URL（または XML）
- 自社から：SP のメタデータ

`shibboleth2.xml` の `<MetadataProvider>` に Entra ID のメタデータを設定します。自前 IdP のときとの違いは、**メタデータの入手元が顧客の Entra ID になる**ことだけです。

**(d) 属性マッピングを設定する**

Entra ID が送出するクレームを、SP のサーバ変数（`REMOTE_USER` 等）にマッピングします。`attribute-map.xml` の調整が必要になる場合があります。

> **ここが実機で最も調整を要する箇所**です。Entra ID が送る属性名（`http://schemas.xmlsoap.org/...` 形式の URI であることが多い）と、PLM が期待する名前を突き合わせます。

**✔ 確認**：`whoami.asp`（または `/PLM/Default.aspx`）で、Entra ID の認証を経て `REMOTE_USER` が表示される

### 第3段階：利用者識別子の対応づけ

**顧客調整で最も重要だった項目**の実装です。

Entra ID から送られてくる識別子（例：`user@customer.com`）と、PLM の利用者 ID（例：`01PLM01`）を対応づけます。

**推奨：対応表を PLM のマスタに持つ**

```
Entra ID の識別子        →  PLM 利用者 ID
user@customer.com        →  01PLM01
another@customer.com     →  01PLM02
```

学習環境では「`@` の前を切り出す」簡易方式でしたが、**本番では対応表方式を推奨**します。理由は、改姓によるメールアドレス変更や、企業統合によるドメイン変更があっても、マスタの1行を更新するだけで済むためです。文字列を加工する方式だと、そのたびに利用者がログインできなくなります。

この対応づけは **PLM 本体の責務**であり、今回作った SSO/JWT の仕組みからは独立しています。`REMOTE_USER` や JWT の `sub` に入る値を、PLM がどう解釈するかという話です。

**✔ 確認**：Entra ID の利用者が、正しい PLM 利用者として認識される

### 第4段階：アプリケーションの配置と動作確認

**参照**：フェーズ2〜6 の README

配置手順は学習環境と同じです。環境固有値（URL、証明書、アカウント、署名鍵）を顧客環境の値にします（「環境固有値一覧」参照）。

- 署名鍵は**顧客環境で新規生成**（フェーズ4）
- アプリケーションプールは**専用の低権限アカウント**（フェーズ6）
- 診断は**無効**、Release ビルド（フェーズ6）

**✔ 確認**：フェーズ3〜6 の全動作確認項目を、顧客環境で実施

### 第5段階：移行とテスト

**参照**：顧客調整項目一覧（9. 移行・テスト計画）

- 既存の独自認証との**並行稼働期間**を設ける
- **切り戻し手順**を用意してから本番切替
- 複数の権限パターンでの受入テスト
- 利用者への周知

## Entra ID 連携で特に注意すべき点

学習環境（Shibboleth IdP）から Entra ID に変わることで、新たに注意が必要になる点です。

### 1. 属性名の違い

自前の Shibboleth IdP は素直な属性名（`mail`、`uid` 等）を送れますが、**Entra ID は URI 形式の長い属性名**を使うことが多いです。

```
http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress
http://schemas.microsoft.com/identity/claims/objectidentifier
```

`attribute-map.xml` でこれらを PLM が使う名前にマッピングします。

### 2. NameID の選択

Entra ID は複数の NameID 形式を選べます。**どれを使うかで識別子設計が変わります**。

| NameID 形式 | 特徴 |
|---|---|
| メールアドレス | 分かりやすいが、変更される可能性がある |
| UPN | ログイン名。比較的安定 |
| ObjectID（永続 ID） | 不変だが人間には読めない。対応表が必須 |

**変更されない ObjectID を軸に、対応表で PLM 利用者に紐づける**のが最も堅牢です。

### 3. 証明書のロールオーバー

Entra ID の署名証明書は**定期的に更新**されます。更新時に SP 側が追随できないと、**ある日突然 SSO が止まります**。

- メタデータを URL で参照し、自動更新される設定にする
- または、更新時に顧客から事前通知を受ける取り決めをする

これは顧客調整項目一覧でも「事前通知が必要な変更」として挙げた項目です。

### 4. 条件付きアクセスと SmartClient

Entra ID の条件付きアクセス（デバイス制限、場所制限、MFA）は**ブラウザには適用されても、SmartClient のダウンロードや API 呼び出しの経路には別の影響**を及ぼす可能性があります。

- ブラウザで SSO 認証 → ここは条件付きアクセスが効く
- SmartClient が引換券を JWT に交換 → **この経路は Entra ID を通らない**（SP 保護外のため）

したがって、**SmartClient の API 経路そのものには Entra ID の条件付きアクセスは効きません**。これは設計どおり（一度 SSO を通れば、その後は JWT で完結する）ですが、顧客のセキュリティ要件によっては別途の考慮が必要です。この点は顧客と認識を合わせておきます。

## この構成が顧客展開に強い理由

改めて、これまでの設計判断が顧客展開でどう活きるかを整理します。

| 設計判断 | 顧客展開での利点 |
|---|---|
| 認証を SP に集約（アプリは REMOTE_USER のみ参照） | **IdP を Entra ID に差し替えても、アプリは無変更** |
| 1アプリ構成（.aspx と API を同居） | サーバ構成がシンプル。ヘッダー詐称リスクが原理的に無い |
| 引換券方式（JWT を直接渡さない） | URL やログに通行証が残らない |
| 署名鍵を資格情報マネージャーに | 設定ファイルに秘密を置かない（監査対応しやすい） |
| 識別子を対応表で解決（推奨） | メールアドレスやドメインの変更に強い |
| 環境固有値を明示（外出しはしない） | どこを変えれば動くかが明確 |

## 顧客ごとの横展開について

2社目以降の顧客に展開する際は、1社目で確定させた次の項目が**標準の土台**になります。

- 識別子の対応表方式
- 署名鍵の保管方式（資格情報マネージャー）
- 保護範囲の標準構成（`/` は保護、`/api` と配布パスは対象外）
- 有効期限の推奨値
- 障害切り分け手順

顧客ごとに変わるのは、Entra ID のテナント固有値、証明書、属性マッピング、識別子の対応関係です。**仕組みそのものは使い回せる**ため、1社目の丁寧な作り込みが、2社目以降を大きく楽にします。

## 完了後

フェーズ7の完了をもって、**独自認証から Entra ID ＋ SSO への移行**という当初の目標が、実際の顧客環境で達成されます。

学習フェーズ（WSL版・Windows版の SSO 構築、JWT のステップ1〜7）から始まり、実装フェーズ（フェーズ1〜7）を経て、**ブラウザは SSO で、SmartClient は JWT で認証する PLM システム**が完成します。

運用フェーズでは、顧客調整項目一覧の「8. 運用・保守」に挙げた責任分界点、障害時の切り分け、事前通知の取り決めが効いてきます。
