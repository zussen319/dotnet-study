# フェーズ6：本番想定の整備

フェーズ5までで、学習環境から組織環境へ再現するための整備が整いました。フェーズ6では、**顧客環境に出す前に「本番相当の状態」で問題が出ないかを確認・整備**します。

このフェーズは、これまでの「機能を作る」フェーズとは性格が異なり、**「本番では緩めていたものを締める」「学習環境では見えなかった問題を洗い出す」**ことが中心です。

> ⚠️ **本フェーズは提案版です。** 実行して判明した点は、これまで同様この冒頭に追記して確定版にしてください。

---

## このフェーズで扱うこと

| # | 項目 | 目的 |
|---|---|---|
| 1 | **低権限アカウントでの動作確認** | フェーズ4で先送りした宿題。権限不足を洗い出す |
| 2 | **診断・デバッグ機能の無効化** | 本番に不要な情報露出を止める |

## 1. 低権限アカウントでの動作確認【フェーズ4の宿題】

学習環境では、アプリケーションプールを管理者アカウント（`infodba`）で動かしていました。**管理者は何にでもアクセスできるため、本来なら発覚するはずの権限不足が表面化しません。** 本番では専用の低権限アカウントで動かすため、ここで一度確認しておきます。

### なぜ重要か

「学習環境では動いたのに、本番で動かない」の典型的な原因が、この権限不足です。本番相当のアカウントで先に確認しておけば、顧客環境での初回トラブルを大幅に減らせます。

### 手順

**(a) 専用アカウントを作成する**（フェーズ4の手順1と同じ）

```cmd
net user plmapp "＜強固なパスワード＞" /add /comment:"PLM app pool identity"
net localgroup IIS_IUSRS plmapp /add
wmic useraccount where "name='plmapp'" set PasswordExpires=false
```

このアカウントは **Administrators グループに入れません**。これが学習環境との違いで、権限不足を洗い出す肝です。

**(b) アプリケーションプールの ID を `plmapp` に変更**

「ユーザープロファイルの読み込み」を True にするのは、フェーズ4と同じです。

**(c) 資格情報を登録し直す**

資格情報は利用者ごとなので、**`plmapp` として登録し直す必要があります**。

```cmd
runas /user:%COMPUTERNAME%\plmapp cmd.exe
```

開いた窓で署名鍵を登録します（フェーズ4の手順4）。

**(d) フォルダ権限を明示的に付与する**

管理者では自動的に通っていた権限を、明示的に付与します。

| フォルダ | 必要な権限 | 無いとどうなるか |
|---|---|---|
| `PlmSsoDemo.Web`（ソース） | 読み取りと実行 | 500 エラー（ページが表示されない） |
| `PlmSsoDemo.Web\App_Data` | 変更（書き込み） | ログが書けない |
| ClickOnce の発行先 | 読み取りと実行 | SmartClient がダウンロードできない |
| `.NET` の一時フォルダ | 通常は既定で付与済み | コンパイルエラー |

`IIS_IUSRS` に対して設定していれば、`plmapp` を `IIS_IUSRS` に入れているため引き継がれます。

### 確認

フェーズ3・4の動作確認項目を**すべて再実行**します。特に次を重点的に見ます。

- `/PLM/Default.aspx` が表示される（＝ソースフォルダの読み取り権限 OK）
- `App_Data\logs\` にログが書ける（＝書き込み権限 OK）
- `/PLM/api/diag` で署名鍵が取得できる（＝資格情報の登録 OK）
- SmartClient が起動しダウンロードできる（＝発行先の権限 OK）

**500 エラーやログの欠落が出たら、それが本番で起きるはずだった問題**です。ここで潰しておきます。

## 2. 診断・デバッグ機能の無効化

学習・検証のために有効化していた機能を止めます。

### (a) 診断エンドポイントを無効化する

`/PLM/api/diag` は設定値や内部状態を返すため、本番では露出させません。

```xml
<add key="DiagEnabled" value="false" />
```

無効化すると 404 を返します。**運用中に状態を確認したくなった場合だけ一時的に true にし、確認後に false へ戻す**運用にします。

### (b) DEBUG ビルド専用機能の確認

フェーズ3で追加した「引換券入力ダイアログ」と、`#if DEBUG` で延ばした有効期限は、**Release ビルドには含まれません**。本番は必ず **Release 構成でビルド**してください。

- ソリューション構成が **Release** になっていること
- `Web.config` の `compilation debug="true"` を **`false`** にすること（下記 3-a）

### (c) ログ出力の方針

ログ（`App_Data\logs\`）は本番でも有用ですが、次を検討します。

- **出力先**：`App_Data` 配下は外部から見えないため安全。このままでよい
- **ローテーション**：現在は日付ごとにファイルが増え続ける。長期運用では定期削除の仕組みを検討
- **内容**：引換券は先頭8文字のみ記録している（全体は残さない）。この方針は維持

## 3. エラー処理の本番化

### (a) 詳細エラーを隠す

`Web.config` を本番向けに変更します。

```xml
<system.web>
  <!-- debug="true" は開発用。本番は false（性能も向上する） -->
  <compilation debug="false" targetFramework="4.8" />

  <!-- エラーの詳細をブラウザに出さない。カスタムエラーページへ誘導 -->
  <customErrors mode="On" defaultRedirect="~/Error.aspx">
    <error statusCode="404" redirect="~/Error.aspx" />
    <error statusCode="500" redirect="~/Error.aspx" />
  </customErrors>
</system.web>
```

`debug="false"` は情報露出を防ぐだけでなく、**タイムアウトやコンパイル最適化の面で本番向き**です。開発用の `debug="true"` のまま本番に出すのは避けるべき、とされています。

### (b) 利用者向けエラーページ

内部のエラー詳細を見せず、PLM の窓口案内などを表示する簡素なページを用意します。API 側（`/PLM/api/*`）は JSON でエラーを返す作りになっているため、主に .aspx 側の話です。

> **注意**：エラーページ自体が SP 保護下にあると、未認証時にリダイレクトループを起こすことがあります。エラーページは保護対象から外すか、認証不要で表示できる作りにします。

### (c) API のエラー応答

現在の API は、失敗理由を JSON で返します（「引換券が無効」「署名が不正」など）。**引換券は短命・一度きりのため情報量は限られますが**、顧客のセキュリティ方針によっては「理由を返さず一律 401」にすることも検討します。ログには詳細を残すので、切り分けは可能です。

## 4. 引換券ストアの共有化（複数台構成の場合のみ）

**単一サーバなら、この章は不要です。** ロードバランサで複数台に分散する構成の場合のみ対象です。

### 問題

現在の `TicketStore` は、**各サーバのメモリ内**に引換券を保管しています。複数台構成では、次の事故が起きます。

```
ブラウザ → サーバA が引換券を発行（サーバA のメモリに保管）
SmartClient → ロードバランサ経由でサーバB に引き換え要求
サーバB のメモリには無い → 「引換券が無効」で失敗
```

### 対策の選択肢

| 方式 | 特徴 |
|---|---|
| **共有ストア（Redis / DB）** | 全サーバが同じストアを見る。最も素直。実装は `TicketStore` の差し替えのみ |
| **セッションアフィニティ**（スティッキー） | ロードバランサで「同じ利用者は同じサーバへ」。引換券の寿命だけ効けばよいので現実的 |
| **引換券に情報を埋め込む** | 引換券自体を署名付きにして、サーバ間で共有不要にする。設計変更が大きい |

### 実装の当たり

`TicketStore` は `Issue` / `Consume` / `Count` という小さな窓口に閉じてあります。**共有ストアに変える場合も、この3メソッドの中身を差し替えるだけ**で、呼び出し側（`Default.aspx`、`TokenController`）は変更不要です。フェーズ3で意図的にこの形にしてあります。

> 顧客環境の構成が固まってから対応する領域です。単一サーバで始めるなら、当面は現状のままで問題ありません。

## 5. HTTPS の徹底

現構成は既に HTTPS のみで動いていますが、本番では HTTP 経路を明示的に塞ぎます。

- **HTTP バインドの扱い**：80 番を残す場合は、HTTPS へリダイレクトする設定を入れる。不要なら 80 番バインドを削除
- **HSTS**：ブラウザに HTTPS を強制するヘッダー。顧客の方針に応じて検討
- **証明書の有効期限**：期限切れの監視。切れると SSO も SmartClient も一斉に止まる

> **ClickOnce との関係**：SmartClient のインストール URL は HTTPS 固定です。HTTP へのリダイレクトが挟まると ClickOnce が失敗することがあるため、**インストール URL は最初から HTTPS を指す**ようにします（これは既に満たしています）。

## 6. 設定値の最終確認

本番に出す前の総点検リストです。

| 設定 | 開発時 | 本番 |
|---|---|---|
| `compilation debug` | `true` | **`false`** |
| `customErrors mode` | `RemoteOnly` | **`On`** |
| `DiagEnabled` | `true` | **`false`** |
| `DevRemoteUser` | （コメントアウト） | **記述ごと削除** |
| `JwtSigningKey`（平文） | （削除済み） | **無いこと** |
| `JwtSigningKeyTarget` | 設定済み | 設定済み |
| ビルド構成 | Debug | **Release** |
| 署名鍵 | 検証用 | **本番用に新規生成** |
| 引換券の有効期限 | DEBUG で 3600 秒 | **Release で 60 秒** |
| JWT の有効期限 | 30 分（または DEBUG 延長） | 業務に合わせて確定 |
| アプリケーションプール ID | `infodba`（管理者） | **`plmapp`（専用・低権限）** |

**特に上位5項目は、情報露出やなりすましに直結**します。チェックリストとして必ず確認してください。

## トラブルシューティング（低権限化で起きやすい問題）

| 症状 | 原因 | 対処 |
|---|---|---|
| ページが 500 エラー | ソースフォルダの読み取り権限不足 | `plmapp`（または `IIS_IUSRS`）に読み取りと実行 |
| ログが出ない | `App_Data` の書き込み権限不足 | 変更権限を付与 |
| 署名鍵が「見つかりません」 | `infodba` で登録した鍵を `plmapp` で読もうとしている | `plmapp` として登録し直す |
| SmartClient がダウンロード失敗 | 発行先フォルダの権限不足 | 読み取りと実行を付与 |
| アプリケーションプールが起動しない | パスワード誤り／期限切れ | イベントログを確認、パスワード再設定 |
| 一部の一時ファイルでエラー | `.NET` 一時フォルダの権限 | 通常は既定で付与済み。まれに ASP.NET の再登録（`aspnet_regiis`）が必要 |
