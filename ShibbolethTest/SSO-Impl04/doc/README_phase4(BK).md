# フェーズ4：署名鍵を Windows 資格情報マネージャーへ

フェーズ3で一連の流れが実環境で通りました。フェーズ4では、**JWT の署名鍵を Web.config の平文から Windows 資格情報マネージャーへ移します**。

**変更するのは「鍵の取得元」だけです。** JWT の発行・検証のロジックには一切手を入れません。したがって、**動作が今までとまったく変わらないことをもって、移行の成功を確認できます**。

> ⚠️ **本フェーズは提案版です。** 実行して判明した点は、これまで同様この冒頭に追記して確定版にしてください。

---

## 先に1点：フェーズ3の Web.config について

いただいた Web.config を拝見したところ、**`DevRemoteUser` が二重に記述されています**。

```xml
<!-- 上部：有効になっている -->
<add key="DevRemoteUser" value="01PLM01@plm-lab.local" />
    ...
<!-- 下部：コメントアウトされている -->
<!-- <add key="DevRemoteUser" value="01PLM01@plm-lab.local" /> -->
```

フェーズ2の Web.config にフェーズ3の設定を追記した際の名残と思われます。エラーにはなりませんが、**有効な行が1つ残っている状態**です。

SSO が正常なうちは実害がありません（REMOTE_USER が優先されるため）。しかし **SP が何らかの理由で REMOTE_USER をセットできなかったとき、エラーにならず黙ってこの利用者として動作してしまいます**。認証の失敗が「別人としての成功」に化けるのは危険なので、**上部の有効な行を削除してください**。

削除後、`/PLM/api/diag` の `devRemoteUser` が「未設定（正しい状態）」になれば正しい状態です。

## なぜ資格情報マネージャーなのか

現状、署名鍵は Web.config に平文で書かれています。この鍵を知っていれば、**誰でも任意の利用者になりすます JWT を偽造できます**。

| 保管方法 | 特徴 |
|---|---|
| Web.config（現状） | ファイルを読めば鍵が分かる。バックアップやソース管理にも残る |
| **資格情報マネージャー**（本フェーズ） | 特定の Windows アカウントの DPAPI で暗号化。ファイルとして存在しない |
| DPAPI ＋ ファイル | 暗号化されるが、ファイルとしては存在する |
| 証明書ストア | RS256（非対称鍵）へ移行する場合に適する |

顧客提供システムでは、**設定ファイルに秘密情報を置かない**ことが求められる場面が多いため、資格情報マネージャー方式を標準としておくと説明しやすくなります。

---

## 重要な前提：資格情報は「利用者ごと」に保管される

**ここがこのフェーズで最も理解が必要な点です。**

Windows の資格情報マネージャーは、**その資格情報を登録した Windows アカウントの DPAPI で暗号化**します。したがって、次の3つが揃わないと Web アプリから読み取れません。

1. **アプリケーションプールを専用アカウントで動かす**
2. **そのアカウントで資格情報を登録する**
3. **アプリケーションプールの「ユーザープロファイルの読み込み」を有効にする**

3 が必要なのは、DPAPI がユーザープロファイルの鍵を使うためです。プロファイルが読み込まれていないと復号できません。

**「登録したのに読めない」というトラブルは、ほぼこの3点のどれかが欠けています。**

## 手順

### 0. フェーズ移行の作業

`SSO-Impl03` → `SSO-Impl04` へコピーする場合は、README_phase3 の「フェーズ移行時の作業」に従ってください（IIS の物理パス付け替え、フォルダ権限、ClickOnce のバージョン確認）。

**フェーズ3の状態で動作確認してから**フェーズ4のファイルを適用すると、切り分けが容易です。

### 1. 専用のローカルアカウントを作成する

コマンドプロンプトを**管理者として実行**します。

```cmd
net user plmapp "＜強固なパスワード＞" /add /comment:"PLM app pool identity"
net localgroup IIS_IUSRS plmapp /add
```

- `IIS_IUSRS` に追加することで、これまで `IIS_IUSRS` に与えたフォルダ権限（ソースフォルダの読み取り、`App_Data` の書き込み）がそのまま効きます
- パスワードの有効期限が切れるとアプリが停止するため、検証環境では無期限にしておくと安全です

```cmd
wmic useraccount where "name='plmapp'" set PasswordExpires=false
```

### 2. アプリケーションプールの実行 ID を変更する

IIS マネージャーで、`/PLM` が使用しているアプリケーションプールを選択します。

**(a) 実行 ID の変更**
「詳細設定」→「プロセス モデル」→「**ID**」→ カスタムアカウント → `.\plmapp` とパスワードを入力

**(b) ユーザープロファイルの読み込み**
同じ「プロセス モデル」内の「**ユーザー プロファイルの読み込み**」を **True** に設定

> ⚠️ **(b) を忘れると資格情報が読めません。** 最も多いつまずきです。

**(c) アプリケーションプールをリサイクル**

### 3. 動作確認（アカウント変更だけの状態で）

まだ資格情報は使いません。**アカウント変更で既存の動作が壊れていないか**を先に確認します。

```
https://sp.plm-lab.local/PLM/Default.aspx
```

- 画面が表示されること（500 エラーならフォルダ権限を確認）
- `App_Data\logs\` にログが書けていること
- `/PLM/api/diag` の `appPoolIdentity` が **`＜マシン名＞\plmapp`** になっていること

**ここで問題があれば、先に解決してください。** 資格情報の話と混ざると切り分けが難しくなります。

### 4. 資格情報を登録する（★このアカウントで実行すること）

資格情報は登録した利用者のものになるため、**`plmapp` として実行する必要があります**。

**(a) `plmapp` としてコマンドプロンプトを起動**

```cmd
runas /user:%COMPUTERNAME%\plmapp cmd.exe
```

パスワードを入力すると、新しいコマンドプロンプトが開きます。**以降の操作はこの窓で行います。**

> 初回は `plmapp` のユーザープロファイルが作成されるため、少し時間がかかります。

**(b) 資格情報を登録**

開いた窓で、スクリプトを実行します。

```cmd
cd /d ＜Tools フォルダのパス＞
powershell -ExecutionPolicy Bypass -File .\Set-JwtSigningKey.ps1
```

ランダムな鍵が生成され、`PlmSsoDemo/JwtSigningKey` という名前で登録されます。自分で鍵を指定する場合は `-Key "＜32バイト以上の文字列＞"` を付けます。

スクリプトを使わず直接登録する場合は次のとおりです。

```cmd
cmdkey /generic:PlmSsoDemo/JwtSigningKey /user:PlmSsoDemo /pass:＜鍵の文字列＞
```

**(c) 登録を確認**

```cmd
cmdkey /list:PlmSsoDemo/JwtSigningKey
```

一覧に表示されれば成功です。**表示されない場合は、別のアカウントで実行している**可能性があります。

### 5. ファイルを配置し、Web.config を変更する

**(a) ファイルの配置**

- `CredentialManager.cs` を `Services\` に**追加**（プロジェクトに含めることを忘れずに）
- `JwtHelper.cs` と `DiagController.cs` を**差し替え**

**(b) Web.config の変更**

```xml
<!-- 追加 -->
<add key="JwtSigningKeyTarget" value="PlmSsoDemo/JwtSigningKey" />

<!-- コメントアウト（動作確認後に削除） -->
<!-- <add key="JwtSigningKey" value="..." /> -->

<!-- 有効な行を削除（前述） -->
<!-- <add key="DevRemoteUser" value="01PLM01@plm-lab.local" /> -->
```

> **`JwtSigningKeyTarget` が設定されている場合、資格情報の取得に失敗しても Web.config には戻りません。** 気づかないまま平文の鍵で動き続けるのを防ぐため、意図的にそうしています。エラーで停止します。

**(c) アプリケーションプールをリサイクル**

## 動作確認

### (1) 診断エンドポイントで取得元を確認する【最重要】

```
https://sp.plm-lab.local/PLM/api/diag
```

次のようになっていれば成功です。

```json
{
  "signingKey": {
    "status": "取得できました（44 バイト）",
    "source": "資格情報マネージャー（PlmSsoDemo/JwtSigningKey）",
    "credentialTarget": "PlmSsoDemo/JwtSigningKey",
    "configKeyStillPresent": "なし（移行完了の状態）"
  },
  "appPoolIdentity": "＜マシン名＞\\plmapp",
  "devRemoteUser": "未設定（正しい状態）"
}
```

**確認の勘所は3点です。**

- `source` が「**資格情報マネージャー**」になっている（Web.config ではない）
- `appPoolIdentity` が **`plmapp`** になっている
- `configKeyStillPresent` が「なし」になっている

### (2) 一連の流れが変わらず動くこと

`https://sp.plm-lab.local/PLM/Default.aspx` から SmartClient を起動し、**フェーズ3とまったく同じ結果**になることを確認します。

**動作が変わらないことが、移行成功の証明です。** 鍵の取得元だけを変えたので、変化があってはいけません。

### (3) ログで取得元を確認する

`App_Data\logs\plmsso-yyyyMMdd.log` に、鍵の取得元が記録されます。

```
[JWT] 発行 sub=01PLM01@plm-lab.local 有効=30分 鍵の取得元=資格情報マネージャー（PlmSsoDemo/JwtSigningKey）
```

### (4) 移行の仕上げ

動作確認が済んだら、**Web.config から `JwtSigningKey` の行を完全に削除**します。コメントアウトのままでは、ファイルを読めば鍵が分かる状態が残ります。

## トラブルシューティング

| 症状 | 原因の候補 | 対処 |
|---|---|---|
| 診断で「資格情報が見つかりません」 | 別のアカウントで登録した | `runas` で `plmapp` として登録し直す（手順4） |
| 同上 | 「ユーザープロファイルの読み込み」が False | アプリケーションプールの詳細設定を確認（手順2-b） |
| 同上 | 資格情報の名前が不一致 | `cmdkey /list` の表示と `JwtSigningKeyTarget` を突き合わせる |
| 画面が 500 エラー | フォルダ権限（アカウント変更が原因） | `plmapp` が `IIS_IUSRS` に入っているか確認 |
| ログが書けなくなった | 同上 | `App_Data` の書き込み権限を確認 |
| アプリケーションプールが起動しない | パスワード誤り／期限切れ | イベントログを確認。パスワードを再設定 |
| `runas` でパスワードを受け付けない | アカウントのポリシー | Computer Management からアカウントを確認 |
| SmartClient が 401（署名が不正） | 鍵が変わったのに古い JWT を使っている | ブラウザを再読み込みして新しい引換券から取り直す |
| 診断で `appPoolIdentity` が変わらない | リサイクルしていない | アプリケーションプールをリサイクル |

**切り分けの順序**は次のとおりです。まず `/PLM/api/diag` で `appPoolIdentity` を確認 → `plmapp` になっていなければ IIS の設定 → なっていれば `cmdkey /list` を `runas` で確認、という流れが確実です。

## うまくいかない場合の代替案：DPAPI ＋ ファイル

`runas` が組織のポリシーで使えない、専用アカウントを作れないなどの事情がある場合は、**DPAPI（マシンスコープ）で暗号化したファイル**に置く方式もあります。

- **利点**：アカウントの制約が無く、導入が簡単
- **欠点**：暗号化されているとはいえ、ファイルとして存在する。同じマシン上のプロセスなら復号できるため、NTFS の ACL で保護する必要がある

顧客のセキュリティ基準次第では、こちらでも十分な場合があります。必要になりましたら実装をご相談ください。

## 本番適用時の追加検討事項

| 項目 | 内容 |
|---|---|
| 鍵のローテーション | 定期的な鍵更新を求められるか。更新時は既存 JWT が全て無効になるため、実施タイミングの調整が必要 |
| 複数台構成 | サーバごとに同じ鍵を登録する必要がある。**登録漏れがあると、そのサーバだけ検証に失敗する** |
| アカウント管理 | `plmapp` のパスワード管理。ドメイン参加環境ではドメインアカウントの選択肢もある |
| バックアップ | 資格情報はバックアップに含まれない。**鍵の控えを別途安全に保管**しておく必要がある |
| 監査 | 誰がいつ鍵を登録・更新したかの記録 |

**特に「複数台構成での登録漏れ」は、本番でありがちな事故**です。1台だけ古い鍵のままだと、そのサーバに振り分けられた利用者だけ認証に失敗し、原因の特定に時間がかかります。診断エンドポイントで各サーバの状態を確認できるようにしておくと、切り分けが容易になります。
