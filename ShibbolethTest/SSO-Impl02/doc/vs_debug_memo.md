このダイアログはボタンの意味が分かりにくいので、まずそこから。

## ダイアログへの回答

「このプロパティページへの変更を元に戻しますか？」と聞かれています。

- **OK** … 変更を元に戻す（設定した Project Url が破棄される）
- **Cancel** … 元に戻さない（設定を保持する）

**「Cancel」を押して設定を残してください。** 仮想ディレクトリの作成に失敗しただけで、URL の設定自体は保持する価値があります。

## 失敗の原因として考えられるもの

VS が IIS の構成を変更できていません。可能性が高い順に挙げます。

**(1) VS が管理者権限で起動していない** ? IIS の構成変更には昇格が必要です。常に管理者起動にされているとのことですが、タイトルバーに「管理者」と表示されているか念のためご確認ください。

**(2) VS がサイトを特定できていない** ? `sp.plm-lab.local` はホスト名付きの HTTPS バインドです。VS は URL からサイトを逆引きしようとしますが、ホストヘッダー付きバインドの場合にこの解決へ失敗することがあります。

**(3) 既にアプリケーションが存在する** ? 手動で `/PLM` を作成済みのため、VS が「作成」しようとして衝突している可能性があります。

## 対処の選択肢

### 案A：.csproj に直接書く（VS に作らせない）

**既に IIS 側は手動で正しく構成できている**ので、VS には「そこを使え」とだけ伝えれば十分です。プロジェクトを閉じ、`PlmSsoDemo.Web.csproj` の末尾（`</Project>` の直前）に次のブロックがあるか確認し、無ければ追加します。

```xml
<ProjectExtensions>
  <VisualStudio>
    <FlavorProperties GUID="{349c5851-65df-11da-9384-00065b846f21}">
      <WebProjectProperties>
        <UseIIS>True</UseIIS>
        <AutoAssignPort>False</AutoAssignPort>
        <DevelopmentServerPort>0</DevelopmentServerPort>
        <IISUrl>https://sp.plm-lab.local/PLM</IISUrl>
        <UseCustomServer>False</UseCustomServer>
        <SaveServerSettingsInUserFile>False</SaveServerSettingsInUserFile>
      </WebProjectProperties>
    </FlavorProperties>
  </VisualStudio>
</ProjectExtensions>
```

既存のブロックがある場合は `<IISUrl>` と `<UseIIS>` を上記に合わせてください。保存後にソリューションを開き直し、F5 を試します。

### 案B：アタッチ方式に統一する（推奨）

**こちらをお勧めします。** 理由は3つあります。

VS にプロジェクト設定を触らせないため、**IIS の構成を完全に自分の管理下に置けます**。今回のようなトラブルが起きません。

フェーズ3以降で使う **(B) の方法（`w3wp.exe` へのアタッチ）と同じ操作**なので、覚えることが減ります。

そして組織でも SmartClient 側のデバッグでは既にこの方式を採用されています。

手順は次のとおりです。

1. プロパティの「Web」タブは触らず、**Cancel で閉じる**
2. ブラウザで `https://sp.plm-lab.local/PLM/Default.aspx` を開く（`w3wp.exe` を起動させるため）
3. VS で「デバッグ」→「プロセスにアタッチ」→「すべてのユーザーのプロセスを表示する」にチェック
4. **`w3wp.exe`** を選択してアタッチ
5. `Page_Load` にブレークポイントを置き、ブラウザを更新すると停止する

**ソースフォルダを直接 IIS にマッピングしているため、コードを修正して保存すれば次のリクエストから反映されます**（WebForms は動的コンパイルのため）。F5 を押さずに済むぶん、むしろ軽快な場合もあります。

## どちらを選ぶか

組織の従来方式（`.aspx` は「ローカル IIS」、SmartClient 側はアタッチ）に合わせたいお気持ちは理解できるので、**まず案Aを試していただき、それでも解決しなければ案Bへ**という進め方が良いと思います。

組織の環境では既に動いている実績があるため、この検証環境固有の事情（ホストヘッダー付き HTTPS バインドなど）が原因の可能性が高いです。案Aで解決すれば、組織環境と同じ操作感を維持できます。

いずれの結果でも、**フェーズ2の完了条件そのものには影響しません**（動作確認は既に通っています）。結果を教えていただければ、フェーズ2を確定版にしてフェーズ3へ進みます。
