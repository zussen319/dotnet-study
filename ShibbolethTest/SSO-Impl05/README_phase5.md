# フェーズ5：組織環境での再現に向けた整備

フェーズ4までで、自宅 PC の Hyper-V 上に一連の仕組みが動く環境ができました。フェーズ5では、**この状態を組織の環境でそのまま再現できるようにする**ための整備を行います。

**目的は「汎用化」ではなく「再現」です。** 設定を外出しして環境を選ばない作りにするのではなく、**どこを変えれば同じものが動くかを明示する**方針で進めます。1環境しかない現段階では、こちらの方が把握しやすく確実です。

> ⚠️ **本フェーズは提案版です。** 実行して判明した点は、これまで同様この冒頭に追記して確定版にしてください。

---

## 前提の確認

| 項目 | 自宅環境 | 組織環境 |
|---|---|---|
| 仮想化基盤 | Hyper-V | Hyper-V（同じ） |
| ゲスト OS | Windows 11 | Windows 11（同じ。将来 Windows Server 2022） |
| ドメイン | `plm-lab.local` | **`plm-lab.local`（変えない）** |
| 開発環境 | VS2026 + .NET 10 → 4.8 | VS2019 / VS2026 いずれも選択可。**最終目標は VS2019** |

### ★推奨：組織では最初から VS2019 で再現する

理由は2つあります。

**最終目標が VS2019 である以上、VS2026 で再現してから移行するのは二度手間**になります。同じ作業を2回行うことになり、その間に環境差の問題が紛れ込む余地も増えます。

そして **VS2019 で開けない・ビルドできない問題があれば、再現の初期段階で発覚する方が安全**です。作り込んだ後に判明するより手戻りが小さくて済みます。フェーズ1で ClickOnce のスパイクを最初に置いたのと同じ考え方です。

そのため本フェーズでは、**まず VS2019 互換性の検証を最優先**で行います。

## 手順

### 1. 互換性をチェックする【最優先】

自宅環境のソリューションフォルダで、チェックスクリプトを実行します。

```powershell
cd ＜Tools フォルダ＞
powershell -ExecutionPolicy Bypass -File .\Check-Vs2019Compat.ps1 -Path C:\work\repos\...\PlmSsoDemo
```

次の5点を確認します。

| # | チェック内容 | 問題があると |
|---|---|---|
| 1 | ソリューションファイルの形式 | **`.slnx` は VS2019 で開けない** |
| 2 | プロジェクトの対象フレームワーク | `net10.0` 等では VS2019 でビルドできない |
| 3 | C# 8.0 以降の構文 | VS2019 でコンパイルエラー |
| 4 | SDK スタイルのプロジェクト | .NET Framework では VS2019 非対応 |
| 5 | NuGet パッケージの対象 | 新しいフレームワークを要求する場合がある |

**`[NG]` と表示されたものは、VS2019 で開く前に必ず解決が必要**です。`[!!]` は目視での確認をお願いします（ラムダ式の `=>` を switch 式と誤検出するなど、誤検知もあります）。

### 2. `.slnx` を `.sln` に変換する

VS2026 が生成する `.slnx` は新しい XML 形式で、**VS2019 では開けません**。従来形式に変換します。

**方法A：VS で名前を付けて保存**

VS2026 で「ファイル」→「ソリューションに名前を付けて保存」から、ファイルの種類に従来形式（`.sln`）を選びます。

**方法B：新規に `.sln` を作り直す**（確実）

1. VS2026 で「ファイル」→「新規作成」→「空のソリューション」を作成（`.sln` 形式を選択）
2. 既存の `.csproj` を2つ追加（「既存のプロジェクトの追加」）
3. スタートアッププロジェクトなどの設定を再現

**変換後は必ず、変換した `.sln` を開いてビルドが通ることを確認**してください。

> **`.slnx` は削除せず残しておく**ことをお勧めします。自宅環境で VS2026 を使い続ける場合に必要です。両方あっても支障ありません。

### 3. C# 7.3 互換性を確認する

チェックスクリプトで `[!!]` が出た箇所を目視で確認します。**フェーズ1〜4のコードはすべて C# 7.3 の範囲で書いてある**ため、通常は問題ないはずです。

念のため、各プロジェクトのプロパティ →「ビルド」→「詳細設定」で言語バージョンを確認します。

- .NET Framework プロジェクトでは「**Automatically selected based on framework version**」（自動的に C# 7.3）のままで正解
- 手動で「最新」に変更しないこと

### 4. 環境固有値を洗い出す

`環境固有値一覧.md` を確認し、組織環境で変更が必要な箇所を把握します。

**ドメイン名（`plm-lab.local`）を変えない方針**であれば、変更箇所は大きく減ります。証明書・SP の設定・IdP のメタデータをそのまま流用できるためです。

主に変わるのは次の7点です。

1. IP アドレス（`hosts`）
2. ソースコードのパス（IIS の物理パス）
3. Windows アカウント名（アプリケーションプールの ID）
4. アカウントのパスワード
5. JWT の署名鍵（**環境ごとに新規生成**）
6. 各種証明書（**環境ごとに新規作成**）
7. マシン名（表示のみ）

### 5. 持ち込むものを準備する

| 分類 | 内容 |
|---|---|
| **手順書** | Windows 版 SSO 構築手順書、フェーズ1〜5の README、環境固有値一覧 |
| **ソース** | `PlmSsoDemo` ソリューション一式（**`.sln` 形式**） |
| **設定ファイルの控え** | `shibboleth2.xml`、`Web.config`、LDIF |
| **インストーラー** | ApacheDS、Tomcat、Shibboleth IdP／SP、OpenJDK |
| **学習資料** | ステップ1〜7の README（JWT の理解のため） |

**除外するもの**

- `bin` / `obj` / `.vs` / `packages` フォルダ … ビルド時に再生成されます
- **署名鍵** … 環境ごとに新規生成するのが原則です
- ClickOnce の発行物 … 組織環境で再発行します

> **ネットワーク制限がある場合**は、NuGet パッケージの復元ができない可能性があります。その場合のみ `packages` フォルダの持ち込みを検討してください。

### 6. 自宅環境で VS2019 相当の確認を行う（任意・推奨）

組織に持ち込む前に、**自宅環境で VS2019 でも開けることを確認**できれば理想的です。自宅 PC に VS2019 を追加インストールできる場合は、この確認をお勧めします。

インストールできない場合は、チェックスクリプトの結果をもって「おそらく大丈夫」と判断し、**組織で最初に開く際に問題があれば対処する**という進め方になります。その際は、本 README のトラブルシューティングを参照してください。

## 組織での再現手順（全体の流れ）

再現作業は、次の順序で進めます。**各段階で動作確認を挟む**のが、切り分けを容易にするコツです。

### 第1段階：SSO 環境の構築

**参照**：Windows 版 SSO 構築手順書

1. Hyper-V に Windows 11 の仮想マシンを作成（**スリープ無効化**）
2. `hosts` に `sp.plm-lab.local` / `idp.plm-lab.local` を登録
3. ルート CA とサーバ証明書を作成、信頼されたルート証明機関に登録
4. ApacheDS を導入、利用者（`01PLM01` 等）を作成
5. **ステップ5の LDIF でグループも作成**（`ou=groups` 配下）
6. OpenJDK ／ Tomcat ／ Shibboleth IdP を導入（8443 で HTTPS）
7. IIS を導入し、**ASP.NET 4.8 を有効化**
8. Shibboleth SP を導入、IdP とメタデータを交換

**✔ 確認**：`https://sp.plm-lab.local/whoami.asp` が SSO 経由で表示される

### 第2段階：開発環境の準備

**参照**：フェーズ2 README の手順0

1. Visual Studio 2019 を導入
2. **「ASP.NET と Web 開発」ワークロード**を導入
3. **`.NET Framework project and item templates`** を個別コンポーネントで追加
   - ※ VS2019 では既定で含まれている可能性が高いですが、テンプレートが出ない場合はこれを確認
4. `.NET Framework 4.8 targeting pack` を確認

**✔ 確認**：「ASP.NET Web アプリケーション (.NET Framework)」テンプレートが表示される

### 第3段階：アプリケーションの配置

**参照**：フェーズ2〜4 の README

1. ソース一式を配置し、**`.sln` を開いてビルド**（NuGet が復元される）
2. IIS にアプリケーション `/PLM` と仮想ディレクトリ `/PLM/smartclient` を作成
3. フォルダのアクセス権を設定（`IIS_IUSRS`：ソースは読み取り、`App_Data` は書き込み）
4. `shibboleth2.xml` に `/PLM` 配下の除外設定を追加（`api` と `smartclient`）
5. アプリケーションプールの ID とユーザープロファイル読み込みを設定
6. 資格情報マネージャーに署名鍵を登録（**そのアカウントで実行**）
7. ClickOnce を発行（インストール URL とパラメーター許可の設定に注意）

**✔ 確認**：フェーズ2〜4 の動作確認項目（環境固有値一覧のチェックリスト参照）

## トラブルシューティング（VS2019 での想定される問題）

| 症状 | 原因の候補 | 対処 |
|---|---|---|
| ソリューションが開けない | `.slnx` 形式 | 手順2で `.sln` に変換 |
| プロジェクトが読み込まれない | SDK スタイルのプロジェクト | 旧形式に変換（今回は該当しないはず） |
| コンパイルエラー（新しい構文） | C# 8.0 以降の構文が混入 | 該当箇所を C# 7.3 の書き方に修正 |
| NuGet の復元に失敗 | ネットワーク制限、パッケージソースの設定 | 社内プロキシの設定、または `packages` フォルダを持ち込む |
| `System.IdentityModel.Tokens.Jwt` のバージョンが合わない | 新しいバージョンが .NET Framework 4.8 非対応 | **6.x 系**を指定する |
| ClickOnce の発行タブが違う | VS のバージョン差 | VS2019 は従来の発行ウィザード。設定項目は同じ |
| ビルドは通るが実行時エラー | アセンブリバインディングの不整合 | `Web.config` の `assemblyBinding` を確認 |

## この先の展開

フェーズ5で組織での再現準備が整います。その後の想定は次のとおりです。

- **フェーズ6：本番想定の整備**（組織での再現が完了してから）
  - `DiagEnabled` の無効化、`customErrors` の `On` 化
  - 低権限アカウントでの動作確認（**フェーズ4で先送りした宿題**）
  - 引換券ストアの共有化（複数台構成の場合）
  - 障害切り分け手順書
- **フェーズ7：顧客環境への適用**
  - 「顧客調整項目一覧」に基づく事前確認
  - Entra ID への接続（IdP の差し替え）
  - Windows Server 2022 での構築

**Windows Server 2022 での構築**は、Windows 版 SSO 構築手順書の §18（Windows Server 2016 の実機知見）が参考になります。TLS 1.2 の有効化、OpenSSL の `-legacy` オプション、既存サイトによるサイト ID のずれなど、サーバ OS 固有の注意点が記録されています。
