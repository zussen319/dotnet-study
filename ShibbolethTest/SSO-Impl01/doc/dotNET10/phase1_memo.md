## 最大の論点：ClickOnce への引換券の渡し方

ステップ6で「引換券を SmartClient の起動パラメータに埋める」と設計しましたが、ClickOnce でこれを実現する方法は .NET のバージョンで事情が変わります。調べた結果は以下のとおりです。

**朗報**：.NET Core 3.1／.NET 5／.NET 6 では `ApplicationDeployment` クラスにプログラムからアクセスできませんでしたが、.NET 7 以降かつ Visual Studio 2022 17.4 以降では、ClickOnce の起動情報を環境変数（`ClickOnce_IsNetworkDeployed`、`ClickOnce_ActivationUri` など）経由で取得できるようになりました。**.NET 10 を使う前提なら、この方式が使えます。**

ただし条件が3つあります。

1. 配置マニフェストの `TrustUrlParameters` が false だと `ActivationUri` は空文字列を返します。発行時に「URL パラメーターの引き渡しを許可する」を有効にする必要があります。
2. クエリ文字列で情報を渡せるのは HTTP(S) で起動される場合のみです。
3. **オンライン専用（インストールしない）にすべき**です。インストール型だと、利用者は初回だけ URL から起動し、以降はスタートメニューのショートカットから起動するため、クエリ文字列を受け取れるのは生涯に一度だけになりがちです。オンライン専用なら常に URL 経由で起動されます。毎回 SSO 経由で引換券を受け取る今回の設計には、オンライン専用が合致します。

**残るリスク**：ブラウザが `.application` を「起動」せず「ダウンロード」してしまうと、利用者がダウンロード後に実行する形になり、その二段階でパラメータが落ちます。Edge の ClickOnce 対応設定に依存する部分です。

そのため、**この一点だけを最初に小さく検証する（スパイク）**ことを強くお勧めします。ここが崩れると設計が変わるためです。代替案は用意してあります（後述）。

## その他、事前に押さえておきたい点

**SP の保護範囲を「パス単位」で分ける必要があります。** メイン画面と引換券発行は SP 保護下に置きたい一方、**SmartClient が叩く `/token/exchange` や `/api/*` は SP 保護から外す**必要があります。SmartClient は SSO セッション（Cookie）を持たないためです。ここは JWT が守ります。

**ClickOnce の配布ファイル自体をどうするかも判断が要ります。** ClickOnce のダウンローダーはブラウザとは別プロセスで、SSO の Cookie を引き継ぐとは限りません。配布パスを SP 保護下に置くとダウンロードに失敗する可能性が高いので、**非保護にするのが現実的**です（引換券が無ければアプリは何もできないので、実害は小さい）。

**Shibboleth SP は IIS Express では動きません。** VS のデバッグ実行を SSO 込みで行うには、フル IIS に発行して `w3wp` にアタッチする形になります。実務では「開発時は REMOTE_USER を疑似的に与えるモード」を用意するのが定石で、これはステップ6のデモ用ヘッダー方式がそのまま流用できます。

**シークレットストアはアプリプール ID の扱いが肝です。** 資格情報マネージャー（ユーザー単位）を使う場合、アプリプールの「ユーザープロファイルの読み込み」を有効にする必要があります。DPAPI（マシンスコープ）ならその制約はありません。

## 署名鍵の保管方式（推奨案）

「本番運用を想定」というご要望から、**Windows 資格情報マネージャー（Credential Manager）＋ アプリプール専用のローカルアカウント**を推奨します。

理由は3点です。秘密がファイルとして存在しない（DPAPI 暗号化ファイルは、暗号化されていても物理的に存在します）。アプリプール専用アカウントにすることで、資格情報の書き込みと ACL 設計が素直になり、本番の運用手順にそのまま流用できる。そして「Windows のシークレットストア」というご要望に最も忠実です。

想定される手間は、専用ローカルアカウントを作り、アプリプール ID をそれに変更し、「ユーザープロファイルの読み込み」を有効にし、そのアカウントで一度資格情報を書き込む、という初期設定です。ここが煩雑だと感じられた場合は、**DPAPI（マシンスコープ）＋ NTFS ACL** に切り替えれば初期設定はぐっと軽くなります。フェーズ4で実際に手を動かしてから判断しても遅くありません。

なお今回の構成では、**鍵を必要とするのは ASP.NET Core のトークンサービスだけ**です。.aspx 側は引換券を取りに行くだけなので、シークレット対応の実装範囲は1アプリに閉じます。

## なぜこれを最初にやるか

いきなり本体を作らず、**「URL のクエリ文字列がアプリに届くか」だけを最小構成で確かめます**。ここが成立しないと、SSO からの引換券の渡し方という設計の根幹が変わるためです。逆に、フェーズ1で判明すれば手戻りはほぼゼロで済みます。

アプリは起動情報を画面に表示するだけで、SSO も JWT も扱いません。判定に必要な情報（環境変数の値、クエリの有無、失敗時の切り分けヒント）が一画面に出るようにしてあります。

## 手順の要点

**発行設定で3つ**が肝です。**オンライン専用**（インストールしない）、**インストール URL を実際の配布 URL に**、そして最重要が「**URL パラメーターの引き渡しを許可する**」（`TrustUrlParameters`）。これが false だと `ActivationUri` が空を返すので、ticket は絶対に届きません。ウィザードにチェックボックスが見当たらない場合は `.pubxml` に直接書く方法も記載しました。

**IIS 側では MIME タイプの追加が必要**です。既定では `.application` や `.manifest` が未登録で、そのままだとリンクが 404 になります。地味ですが必ず踏む箇所なので、表にまとめてあります。

なおこの段階では **SP の保護は掛けません**。素の状態で通してから、フェーズ2で保護範囲を設計します。

## 判定の勘所

テストページに3つのリンクを用意しました。特に見ていただきたいのは **(2) のランダムな引換券**です。本番では引換券は毎回変わるため、初回の値がキャッシュされて使い回されると設計が成立しません。ここが通れば安心して先に進めます。
