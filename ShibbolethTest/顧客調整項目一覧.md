# PLM システム SSO 対応：顧客と調整すべき設計項目

Entra ID ＋ Shibboleth SP による SSO と、SmartClient の JWT 認証を顧客環境へ適用するにあたり、**事前に顧客と合意しておくべき設計項目**の一覧です。

学習フェーズ（ステップ1〜7）と実装フェーズ（フェーズ1〜3）で実際に判明した制約・知見を反映しています。

---

## 特に先に固めるべき5項目

調整に時間がかかる、または後から変更すると手戻りが大きい項目です。**これらは初回の打ち合わせで議題に挙げることをお勧めします。**

| # | 項目 | 理由 |
|---|---|---|
| 1 | **利用者識別子の対応関係** | PLM の全機能・全データが利用者 ID に紐づくため、後からの変更は影響範囲が極めて大きい |
| 2 | **Entra ID から送出する属性（クレーム）** | 顧客の IT 部門でのアプリ登録作業が必要。決まらないと SP の設定も確定しない |
| 3 | **サーバ証明書とコード署名証明書の調達** | 発行・承認に時間がかかることが多く、無いと ClickOnce 配布と HTTPS が成立しない |
| 4 | **条件付きアクセス・MFA の適用範囲** | SmartClient の動作に影響する可能性があり、後から判明すると設計変更になる |
| 5 | **既存「独自認証」からの移行方式と並行稼働期間** | 移行計画そのもの。切り戻し手順を含めて合意が必要 |

---

## 1. 認証基盤（Entra ID）

顧客の IT 部門が主管する領域です。**自社側では変更できない**ため、早期の確認が重要です。

| 項目 | 確認・調整すべき内容 | 決まらないと困ること |
|---|---|---|
| アプリケーション登録 | Entra ID にエンタープライズアプリケーション（SAML）を登録できるか。申請手続きと所要期間 | SSO 自体が始められない |
| メタデータの交換 | 顧客からフェデレーションメタデータ URL の提供を受けられるか。自社 SP のメタデータをどう渡すか | SP と IdP の信頼関係が構築できない |
| **NameID の形式と値** | `emailAddress` / UPN / `persistent` のどれか。実際に入る値の例 | `REMOTE_USER` の形式が決まらず、識別子設計が確定しない |
| 送出する属性 | メールアドレス、UPN、表示名、所属グループなど、何を送ってもらうか | 属性が足りないと PLM 側で情報を補完できない |
| 署名証明書の更新 | IdP の署名証明書の有効期限と更新（ロールオーバー）の運用。**更新時に事前通知をもらえるか** | 証明書更新のたびに突然 SSO が停止する |
| MFA・条件付きアクセス | 適用の有無と条件（場所・デバイス・リスクなど） | SmartClient の起動やダウンロードが想定外にブロックされる |
| ゲスト（B2B）ユーザー | 外部委託先などのゲストアカウントを PLM で使うか | ゲストは属性が異なる場合があり、識別子設計に影響 |
| シングルログアウト（SLO） | 必要か。必要な場合の期待動作 | 実装範囲が変わる |
| 検証用テナント | 開発・検証環境で使えるテナントまたはアプリ登録があるか | 本番でしかテストできない状況になる |

## 2. 利用者識別子とアカウント運用

**最も重要な領域**です。ここを誤ると全機能に影響します。

| 項目 | 確認・調整すべき内容 | 決まらないと困ること |
|---|---|---|
| **識別子の対応関係** | PLM の利用者 ID（例：`01PLM01`）と Entra ID の識別子（例：`01PLM01@example.com`）をどう対応づけるか | 認証はできても「誰か」が特定できない |
| 正規化ルール | `@` の前を切り出すのか、対応表を PLM 側に持つのか。**対応表方式が安全**（メールアドレス変更に強い） | ドメイン変更・改姓等で利用者が PLM にログインできなくなる |
| 大文字小文字の扱い | 識別子の大小を区別するか。Entra ID から送られる値の実際の表記 | 同一人物が別人として扱われる |
| アカウント登録の流れ | 新入社員・異動時に、誰がいつ PLM 側の利用者を登録するか | 入社しても PLM が使えない期間が発生 |
| 退職・異動時の扱い | Entra ID で無効化されたら PLM 側もどうするか。**プロビジョニング（SCIM 等）の自動化は行うか** | 退職者が PLM にアクセスできる状態が残る |
| 例外的なアカウント | 共用アカウント、バッチ処理用、外部委託先、システム管理者用 | SSO では認証できない利用者が発生 |
| 認証できない場合の代替 | IdP 障害時の緊急ログイン手段を用意するか | IdP 障害＝業務完全停止 |

> **推奨**：識別子は「対応表を PLM のマスタに持つ」方式が最も安全です。メールアドレスの文字列に依存しないため、改姓やドメイン統合の影響を受けません。

## 3. ネットワーク・DNS・証明書

| 項目 | 確認・調整すべき内容 | 決まらないと困ること |
|---|---|---|
| PLM サーバのホスト名 | FQDN の決定と DNS 登録。**証明書のホスト名と完全一致が必要** | ClickOnce は証明書エラーを無視できず起動しない |
| **サーバ証明書** | 社内 CA（AD CS）かパブリック認証局か。発行申請の手続きと期間、更新運用 | HTTPS が成立せず、SmartClient も動作しない |
| **クライアントの CA 信頼** | 社内 CA の場合、ルート証明書を全端末に配布済みか（GPO / Intune） | 一部の端末だけ SmartClient が起動しない |
| **コード署名証明書** | ClickOnce のマニフェスト署名に使う証明書。社内 CA で発行するか、パブリックか | 「発行元を確認できません」の警告が毎回出る／ポリシーで起動が阻止される |
| プロキシ・ファイアウォール | クライアント → PLM、PLM サーバ → Entra ID の到達性。プロキシ認証の有無 | 通信が届かず SSO が完結しない |
| 社外からの利用 | VPN 経由のみか、インターネット公開か | 公開する場合はセキュリティ要件が大きく変わる |
| 時刻同期 | サーバ・クライアントの NTP 設定 | SAML アサーションや JWT の有効期限判定が失敗する |

## 4. サーバ構成・IIS

| 項目 | 確認・調整すべき内容 | 決まらないと困ること |
|---|---|---|
| OS・IIS のバージョン | Windows Server のバージョン。**TLS 1.2 の有効化状況** | SP や .NET が想定どおり動作しない |
| Shibboleth SP の導入 | 顧客サーバへのインストール可否と、導入作業の担当 | SSO の前提が整わない |
| **保護範囲（パス単位）** | メイン画面は保護、API と ClickOnce 配布は保護対象外、という設計の合意 | SmartClient がダウンロードも API 呼び出しもできない |
| ASP.NET 4.8 の有効化 | IIS の機能として導入済みか | アプリが動作しない |
| 複数台構成 | ロードバランサの有無、台数 | **引換券のストアを共有化する実装が追加で必要**になる |
| SSL 終端の位置 | ロードバランサで終端するか、IIS で終端するか | SP の設定（`<Site>` の scheme/port）が変わる |
| 環境の数 | 開発・検証・本番。それぞれに SP と IdP 設定が必要 | 検証できないまま本番投入になる |
| アプリケーションプール | 専用アカウントを作成できるか（署名鍵の保管方式に影響） | 資格情報マネージャー方式が使えない |

## 5. JWT・トークン設計（SmartClient 認証）

| 項目 | 確認・調整すべき内容 | 決まらないと困ること |
|---|---|---|
| 署名方式 | HS256（共通鍵）か RS256（公開鍵）か。**検証する側が複数に分かれるなら RS256** | 後からの変更は鍵配布の設計変更を伴う |
| **署名鍵の保管** | Windows 資格情報マネージャー / 証明書ストア / その他。顧客のセキュリティ基準に適合するか | セキュリティ監査で指摘を受ける |
| 鍵のローテーション | 定期的な鍵更新を求められるか。その際の手順と停止時間 | 運用開始後に対応できない |
| 有効期限の設計 | 引換券（数十秒）、JWT（数十分）の妥当性。**顧客の業務実態に合うか** | 作業中にトークンが切れて業務が中断する |
| 権限剥奪の反映速度 | 権限変更が何分以内に反映されるべきか | セキュリティ要件を満たせない |
| 監査ログ | 認証・トークン発行の記録要件（項目・保管期間） | 監査対応ができない |

## 6. SmartClient（ClickOnce）配布

**実装フェーズで判明した制約が多い領域**です。

| 項目 | 確認・調整すべき内容 | 決まらないと困ること |
|---|---|---|
| **ブラウザの ClickOnce 対応** | 標準ブラウザは何か。ClickOnce の起動が有効か（Edge のポリシー設定） | リンクをクリックしてもダウンロードされるだけで起動しない |
| 配布形態 | オンライン専用（インストールしない）で合意できるか | インストール型では**起動パラメータを毎回受け取れない**（設計が成立しない） |
| クライアント要件 | .NET Framework 4.8 の導入状況、OS バージョン | 一部端末で起動しない |
| 端末ポリシー | アプリケーション実行の制限（AppLocker 等）の有無 | 起動がブロックされる |
| 更新の運用 | バージョン管理と更新の反映タイミング | 利用者が古いバージョンを使い続ける |
| 既存 SmartClient との関係 | 現行の SmartClient を置き換えるのか、並行稼働するのか | 移行方式が決まらない |

> **実装フェーズでの確認結果**：ClickOnce の起動パラメータ受け渡しは、**オンライン専用**かつ**「URL パラメーターの引き渡しを許可」**の設定が必須です。インストール型では利用者が2回目以降スタートメニューから起動するため、引換券を受け取れません。

## 7. 認可・権限設計

今回の実装範囲外ですが、**本番適用時には必ず論点になります**。

| 項目 | 確認・調整すべき内容 | 決まらないと困ること |
|---|---|---|
| 権限情報の所在 | PLM のマスタで持つか、Entra ID のグループから受け取るか | 権限管理の運用主体が決まらない |
| 既存権限との整合 | 現行 PLM の権限体系をそのまま維持するか | 移行時に権限が変わり業務影響が出る |
| 部門・プロジェクト単位の制御 | データの可視範囲の要件 | 見えてはいけないデータが見える |
| 権限変更の運用 | 誰がいつ変更するか。反映までの時間 | 運用が回らない |

## 8. 運用・保守

| 項目 | 確認・調整すべき内容 | 決まらないと困ること |
|---|---|---|
| **責任分界点** | Entra ID・端末・ネットワークは顧客、SP と PLM は自社、という切り分けの明文化 | 障害時に責任の所在で紛糾する |
| 障害時の切り分け | ログの提供範囲、初動の連絡先、エスカレーション経路 | 復旧が遅れる |
| 事前通知が必要な変更 | IdP の証明書更新、条件付きアクセスの変更、テナント設定変更 | **予告なく SSO が停止する** |
| ログの保管 | 保管期間、保管場所、個人情報の扱い | 監査・調査に対応できない |
| 定期メンテナンス | 実施可能な時間帯、停止可能時間 | 更新作業が実施できない |
| 問い合わせ窓口 | 利用者からの「ログインできない」の一次受付はどちらか | 利用者が困る |

## 9. 移行・テスト計画

| 項目 | 確認・調整すべき内容 | 決まらないと困ること |
|---|---|---|
| **移行方式** | 一斉切替か段階移行か | 計画が立たない |
| **並行稼働期間** | 独自認証と SSO を並行させる期間の有無と長さ | 切り戻しができない |
| 切り戻し手順 | 問題発生時に独自認証へ戻す手順と判断基準 | 障害時に業務が止まる |
| テスト用アカウント | 検証に使えるアカウントの提供（複数の権限パターン） | 十分なテストができない |
| 受入テストの範囲 | 顧客側で実施する確認項目と合格基準 | 検収でもめる |
| 利用者への周知 | ログイン方法変更の案内、実施主体とタイミング | 当日に問い合わせが殺到する |
| 教育・マニュアル | 利用者向け・管理者向けの資料をどちらが用意するか | 準備漏れ |

## 10. 打ち合わせ用の確認質問（例）

初回打ち合わせでそのまま使える形の質問です。

**認証基盤について**
- Entra ID にエンタープライズアプリケーション（SAML）を登録する手続きと、所要期間を教えてください
- SAML の NameID として、どの形式・どの値を送出いただけますか（実際の値の例もいただけますか）
- メールアドレス以外に送出可能な属性を教えてください
- IdP の署名証明書更新について、事前通知はいただけますか
- MFA や条件付きアクセスの適用状況を教えてください

**利用者について**
- 現在の PLM 利用者 ID と、Entra ID のアカウントの対応関係を教えてください
- 入社・退職・異動時のアカウント運用フローを教えてください
- 共用アカウントや外部委託先の利用があれば教えてください

**証明書・端末について**
- PLM サーバのサーバ証明書は、どちらで発行いただけますか
- 社内 CA の場合、ルート証明書は全端末に配布済みでしょうか
- クライアントアプリのコード署名証明書はご用意いただけますか
- 標準ブラウザと、ClickOnce アプリケーションの起動可否を教えてください

**移行について**
- 移行の希望時期と、並行稼働期間のご希望を教えてください
- 検証用に使えるアカウントとテナント（またはアプリ登録）をご提供いただけますか

## 補足：自社側で先に決めておくとよいこと

顧客との調整の前に、自社内で方針を持っておくと議論が進みやすい項目です。

- **識別子の対応表方式を標準とするか**（メールアドレス依存を避ける設計）
- **署名鍵の保管方式の標準**（顧客ごとに変えると保守が煩雑になる）
- **有効期限の推奨値**（引換券・JWT）とその根拠
- **保護範囲（パス単位）の標準構成**（`/` は保護、`/api` と配布パスは対象外）
- **顧客ごとの環境差をどこで吸収するか**（設定ファイルか、ビルド時か）
- **障害切り分け手順書**（どのログを見れば何が分かるか）

これらは、複数の顧客に展開する際の**標準化の土台**になります。1社目の適用時に決めておくと、2社目以降が大幅に楽になります。
